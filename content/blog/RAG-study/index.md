## 왜 이 글을 읽었나

RAG(Retrieval-Augmented Generation)를 단순히 이론으로만 알고 있었는데, 실제 프로덕션 코드베이스에 어떻게 적용하는지 궁금했습니다. 특히 "코드를 검색 대상으로 삼는다"는 접근이 생소하고 흥미로웠습니다. 벡터 검색이 코드에 잘 맞지 않아서 시행착오를 겪은 부분도 솔직하게 공유되어 있어 실용적인 내용이 많았습니다.

## 1. 문제 상황 — 문서와 코드의 불일치

포스타입은 PRD(제품 요구사항 정의서)와 테크 스펙을 꼼꼼히 기록하는 문화가 있는 조직이라고 합니다. 하지만 배포 주기가 빨라지면서 구조적인 문제가 생겼습니다.

```
문서 업데이트 속도 < 코드 변경 속도

→ 문서와 실제 동작이 달라짐
→ 문서가 신뢰를 잃고 방치
→ 결국 코드를 직접 봐야만 정확한 스펙을 알 수 있음
```

특히 신규 입사자가 많이 합류하면서 병목이 심해졌습니다.

- **PM / CX** : 현행 로직을 확인하려면 매번 개발팀에 질문해야 했고, 답변을 기다리는 동안 의사결정이 늦어졌습니다.
- **엔지니어** : 잦은 질의로 개발 흐름이 자주 끊겼습니다.

이 문제를 해결하기 위해 포스타입이 내린 결론은 하나였습니다.

> **"코드가 항상 최신 스펙이다"**
> 그러니 코드를 검색 대상으로 삼는 RAG 챗봇을 만들자.

---

## 2. RAG(Retrieval-Augmented Generation)란?

RAG는 LLM이 답변하기 전에 신뢰할 수 있는 외부 지식을 먼저 검색하고 참고하도록 하는 기술입니다.

### 왜 RAG가 필요한가

일반 LLM에는 세 가지 한계가 있습니다.

```
1. 도메인 특화 지식 부재
   → 우리 서비스의 비즈니스 로직은 LLM이 모름

2. 환각(Hallucination)
   → 모르는 것을 아는 척 지어낼 수 있음

3. 최신 정보 부재
   → 학습 이후 변경된 내용은 반영 안 됨
```

RAG는 이를 보완합니다. 질의가 들어오면 LLM에 바로 전달하지 않고, 사전에 구축해둔 지식 베이스에서 관련 문서를 먼저 검색한 뒤 그 내용을 함께 LLM에 전달합니다.

### RAG 동작 흐름

```
사용자 질문
    ↓
[Retrieval] Knowledge Base에서 관련 문서 검색
    ↓
[Augmentation] 질문 + 검색된 문서를 하나의 프롬프트로 결합
    ↓
[Generation] LLM이 보강된 지식을 바탕으로 최종 답변 생성
```

포스타입의 예시를 보면 이해가 쉽습니다.

```
Q: 리퀘스트 결제 시 예치금은 언제 확정되나요?

[Retrieval] → TransactionReserved.java, RequestPayment.java 검색됨
[Augmentation] → 코드 주석 + 로직 + 질문을 결합
[Generation] → LLM이 답변 생성

A: 리퀘스트 결제 시 예치금은 결제 완료일로부터 7일 후 확정됩니다.
```

## 3. 기술 스택 선택

포스타입은 익숙한 AWS 생태계를 기반으로 구성했습니다.

| 역할 | 선택한 서비스 | 이유 |
|------|-------------|------|
| Data Source | Amazon S3 | 원본 코드 문서 저장 |
| Embedding Model | Titan Text Embeddings V2 | AWS 네이티브 연동 |
| Vector DB | OpenSearch Serverless | Hybrid 검색 지원 (이유는 뒤에) |
| LLM | Claude 3.5 Sonnet | 높은 이해도, Bedrock 연동 용이 |
| 통합 관리 | AWS Bedrock Knowledge Base | 업로드 ~ 검색까지 통합 관리 |

**AWS Bedrock Knowledge Base**를 선택한 핵심 이유는 문서 업로드, Embedding, Indexing, 검색을 통합으로 관리할 수 있고, S3에 문서를 올리면 자동 동기화가 가능하다는 편의성 때문이었습니다.

## 4. 핵심 과제 1 — Chunking 전략

RAG 시스템의 성능은 데이터 구조에 직결됩니다. Embedding 모델은 한 번에 처리할 수 있는 텍스트 길이에 제한이 있고, 너무 긴 청크는 검색 정확도를 떨어뜨립니다.

### 청크가 너무 크면 생기는 문제

```
1,000줄짜리 Java 파일 전체 = 하나의 청크

"결제 완료 처리 메서드"를 검색
→ 관련 없는 코드까지 함께 검색됨
→ 노이즈 증가 → 답변 품질 하락
```

### Bedrock KB의 Chunking 전략 종류

- **고정 크기**: 설정한 토큰 수로 기계적 분할. 문맥이 중간에 잘릴 수 있음.
- **의미 체계**: 의미 단위로 분할해 문맥 유지. 자연어 문서에 적합.
- **계층 구조**: 부모-자식 계층으로 분할. 하위 노드가 상위 컨텍스트를 포함.
- **없음 (None)**: 사전에 직접 분할한 경우 사용.

### 포스타입의 선택 — 메서드 단위 사전 파싱

코드를 검색 대상으로 삼았기 때문에 코드의 구조적 특성을 활용했습니다.

```
임의로 자른 코드 → 의미가 없음
메서드 단위로 파싱 → 각 메서드가 하나의 완결된 청크

→ Chunking 전략: None (직접 분할)
```

추가로 두 가지를 더 했습니다.

1. **도메인 사전 구축**: 코드 내 도메인 명칭 + 도움센터의 한국어 키워드를 매핑한 사전을 만들어 자연어 질의와 코드 사이의 간극을 줄임
2. **오류 문구, 유효성 검증 포함**: 코드 내 에러 메시지, 검증 로직도 파싱해 포함

## 5. 핵심 과제 2 — Metadata Filtering

### 첫 번째 실패

청크 전략까지 완성하고 테스트했는데 결과가 좋지 않았습니다. 원인은 RAG의 기본 검색 방식에 있었습니다.

```
RAG 기본 검색: 전체 문서 중 TOP-K개 선택

전체 문서 4,400여 개
"포인트" 관련 질의 → 상위 5개 검색

→ 포인트 관련 코드가 수백 개인데 5개만 가져옴
→ 일부만 부합해도 응답으로 반환
→ 전혀 상관없지만 키워드가 비슷한 코드가 포함되기도
```

### 해결책 — Metadata Filtering

단순히 코드 텍스트만 저장하는 것이 아니라, 각 코드에 **메타데이터**를 붙여서 검색 범위를 좁히는 방법입니다.

```json
{
  "metadataAttributes": {
    "documentType": "source_code",
    "className": "NotificationService",
    "domain": "notification",
    "module": "domain",
    "package": "com.example.notification",
    "relatedEvents": ["NotifyEvent"],
    "callsTo": ["NotificationRepository.save"]
  }
}
```

이제 챗봇은 질의를 받으면 질문에서 도메인과 키워드를 추출하고, 해당 도메인에 속한 코드만 검색 대상으로 좁힙니다.

```
"알림이 발송되는 케이스를 모두 알려줘"

→ domain == notification, relatedEvents == NotifyEvent 추출
→ 4,400개 → 약 50개로 축소
→ 정밀한 탐색 가능
```

메타데이터 필터링의 핵심은 **"어디서 찾아야 할지"를 검색 엔진에게 알려주는 것**입니다. 막연한 추측이 아닌 정밀한 탐색으로 바뀌는 것이죠.

## 6. 핵심 과제 3 — 검색 방식: Hybrid Search

### Semantic 검색만으로는 부족한 이유

Bedrock KB는 기본적으로 **Semantic(의미 기반) 검색**을 사용합니다. 텍스트를 벡터로 변환해 의미적 유사도를 계산하는 방식입니다.

```
"결제 완료 처리" 검색
→ processTransaction() 반환 (의미적으로 유사)
→ finishOrder() 반환 (의미적으로 유사)
→ completePayment() 반환 (찾던 것)
```

문제는 코드에는 **정확한 식별자(identifier)가 있다**는 점입니다. 메서드명, 클래스명은 정확히 검색해야 할 때가 많습니다.

또한 **OOV(Out-of-Vocabulary) 문제**도 있습니다. Embedding 모델이 학습하지 않은 도메인 특화 용어(`completePayment` 같은 커스텀 식별자)는 벡터 표현이 부정확할 수 있습니다.

### Keyword 검색만으로도 부족한 이유

반대로 키워드 검색만 사용하면 의미 기반 탐색이 어렵습니다. "결제 완료"를 "payment completion"으로 물어봤을 때 키워드 매칭이 안 될 수 있죠.

### 해결책 — Hybrid Search + RRF

두 검색 방식을 동시에 사용한 뒤 **RRF(Reciprocal Rank Fusion)** 알고리즘으로 결과를 결합합니다.

```
Semantic 검색 결과:  [A(1위), B(2위), C(3위), D(4위)]
Keyword 검색 결과:   [C(1위), A(2위), E(3위), B(4위)]

RRF 결합:
A의 점수 = 1/(1+k) + 1/(2+k)   ← 양쪽 상위
C의 점수 = 1/(3+k) + 1/(1+k)   ← 키워드 1위, 시맨틱 3위

→ 두 방식 모두 상위에 있는 문서가 최종 상위권에 위치
```

핵심 아이디어는 **"두 방식 모두에서 높은 순위에 있는 문서를 최종 상위로 올린다"** 는 것입니다.

> **Hybrid Search를 위해 OpenSearch Serverless를 선택한 이유**
> AWS Bedrock KB에서 Hybrid 검색은 관리형 OpenSearch가 아닌 Serverless 방식에서만 지원됩니다. Serverless는 사용하지 않는 시간에도 기본 비용이 발생한다는 단점이 있지만, Hybrid 검색을 위해 이를 감수했습니다.

## 7. 고민 끝에 사용하지 않기로 한 것 — Rerank

검색 품질을 더 높이기 위해 **Rerank**도 검토했습니다. 검색 결과를 별도 모델로 한 번 더 재정렬하는 기술입니다.

```
일반: 질문 → 검색 → 결과
Rerank: 질문 → 검색 → 1차 결과 → Rerank 모델 → 2차 결과
```

하지만 테스트 결과 **코드에는 오히려 역효과**가 있었습니다.

```
문제:
Rerank 모델은 자연어 기준으로 학습됨
→ 코드의 구문적 맥락을 자연어처럼 해석하려 함
→ 정확히 키워드 매칭된 문서의 순위를 오히려 뒤로 밀어냄

결론: Rerank 미사용
```

이 결정이 인상적이었습니다. 기술을 도입하는 것보다 **"이 기술이 우리 문제에 맞는가"를 먼저 검증**한 것이죠.

## 8. 자동 동기화 파이프라인 — "코드가 최신 스펙"을 유지하는 방법

RAG 챗봇이 잘 동작해도, 코드가 바뀌면 KB도 함께 업데이트되어야 합니다. 이를 위해 **배포와 연동된 자동 동기화 파이프라인**을 구축했습니다.

```
운영 배포 완료 (AWS CodePipeline 트리거)
        ↓
코드 파싱 (메서드 단위 + 메타데이터 추출)
        ↓
S3에 문서 업로드
        ↓
Bedrock KB Ingestion Job 트리거
        ↓
증분(Incremental) 업데이트
        ↓
5분 내 KB 업데이트 완료
```

**증분 업데이트**가 핵심입니다. 전체를 다시 색인하지 않고, 변경된 부분만 업데이트하기 때문에 5분 내로 반영이 가능합니다.

## 9. 내가 배운 것

### RAG의 성능은 알고리즘보다 데이터 품질에 달려 있다

"아무리 좋은 모델을 써도 원본 문서가 적절히 준비되어 있지 않으면 좋은 답변을 얻을 수 없다"는 말이 인상 깊었습니다. 청크 전략, 메타데이터 설계가 모델 선택보다 훨씬 중요한 경우가 많다는 걸 배웠습니다.

### 코드는 자연어와 다른 검색 전략이 필요하다

Semantic 검색은 자연어에 최적화되어 있습니다. 코드처럼 정확한 식별자가 중요한 대상에는 Keyword 검색을 함께 써야 하고, Rerank처럼 자연어 기준으로 학습된 모델은 오히려 역효과를 낼 수 있습니다. 도메인 특성에 맞는 검색 전략을 선택하는 것이 중요합니다.

### Metadata Filtering은 벡터 검색의 정밀도를 높이는 핵심 도구다

4,400개 중 TOP-K를 뽑는 것과 50개로 범위를 좁힌 뒤 TOP-K를 뽑는 것은 결과가 완전히 다릅니다. 좋은 메타데이터 설계가 검색 품질을 결정한다는 것을 배웠습니다.

### 문서화 vs 코드 = 코드가 항상 이긴다

아무리 좋은 문서화 문화가 있어도, 빠른 배포 속도 앞에서 문서는 금방 뒤처집니다. "코드가 최신 스펙이다"라는 전제를 받아들이고, 코드 자체를 지식 베이스로 삼는 접근이 현실적이라는 것을 배웠습니다.

### 배포 파이프라인과 지식 베이스 동기화

CI/CD 파이프라인 완료 시점에 KB 업데이트를 트리거하는 설계가 깔끔했습니다. 운영 배포 = 스펙 업데이트가 자동으로 이루어지는 구조입니다.

## 10. 더 공부하고 싶은 것

- **RRF(Reciprocal Rank Fusion) 알고리즘**: 두 랭킹을 결합하는 수식이 궁금합니다. 단순 평균과 어떻게 다른지, k 값이 결과에 어떤 영향을 주는지 직접 계산해보고 싶습니다.
- **임베딩 모델 비교**: Titan Embeddings V2 외에 OpenAI, Cohere 등 다른 임베딩 모델과 성능 차이가 얼마나 나는지 궁금합니다.
- **2부 내용**: 실제 챗봇 구현과 에이전트(Agent)로의 발전 과정이 어떻게 이어지는지 기대가 됩니다.
- **벡터 DB 비교**: OpenSearch Serverless 외에 Pinecone, pgvector, Weaviate 등과의 트레이드오프가 궁금합니다.
