# LangChain 이해 — 기본 Chain에서 RAG, Agent와 관찰성까지

LLM에 질문을 보내고 답변을 받는 기능은 비교적 짧은 코드로 만들 수 있다. 그러나 고객 문의를 분류하고, 이전 대화를 참고하며, 주문 상태나 사내 규정을 조회하는 서비스를 만들려면 모델 호출 밖의 구조가 필요하다.

모델의 답변을 프로그램이 처리할 수 있는 형식으로 바꾸고, 필요한 정보를 제공하며, 외부 기능의 실행 결과를 다시 모델에 전달해야 한다. 여러 작업의 실행 순서와 실패 처리, 대화 상태도 관리해야 한다.

**LangChain은 모델과 데이터, 도구를 공통 인터페이스로 연결해 AI 애플리케이션의 실행 흐름을 구성하는 프레임워크다.** 이를 이해하는 핵심은 API 이름을 외우는 것보다 각 블록의 입력과 출력, 실행 주체, 상태의 위치를 구분하는 데 있다.

```text
사용자 입력
  → Prompt로 모델의 작업 정의
  → Model로 해석·생성
  → Parser 또는 Schema로 출력 정리
  → Memory로 이전 맥락 제공
  → Tool로 외부 정보 조회·작업 실행
  → 순차·병렬·분기로 처리 흐름 구성
  → RAG로 문서 근거 제공
  → Agent로 필요한 작업을 동적으로 선택
  → LangGraph로 상태와 전이 제어
  → LangSmith로 실제 실행 경로 관찰
```

이 흐름은 모든 요청이 반드시 거쳐야 하는 실행 순서가 아니다. 애플리케이션에 필요한 기능을 점진적으로 조립하는 개념적 순서다. 단순한 분류 서비스에는 구조화 출력까지만 필요할 수 있고, 규정 검색 서비스에는 고정된 RAG Chain만으로 충분할 수 있다.

> 예시는 LangChain 1.x 기반 학습 코드의 구조를 바탕으로 설명용으로 축약했다. 코드 블록마다 필요한 앞 단계 객체가 있다고 가정하는 부분이 있으며, 전체 실행 파일을 대체하는 설치·실행 가이드는 아니다.

## 1. LangChain, LangGraph, LangSmith의 역할

이름이 비슷한 세 도구는 서로 다른 문제를 다룬다.

| 도구 | 중심 역할 | 설계할 때의 질문 |
|---|---|---|
| LangChain | 모델·프롬프트·도구 등 연결, Chain과 Agent 구성 | 어떤 기능을 어떻게 조립할 것인가? |
| LangGraph | 상태를 가진 Workflow와 Agent의 실행 제어 | 어떤 상태에서 어떤 노드를 실행할 것인가? |
| LangSmith | 실행 추적, 디버깅, 평가 | 실제로 무엇이 실행됐고 결과가 적절했는가? |

LangChain의 `create_agent()`는 LangGraph 기반의 실행 구조를 사용한다. 복잡한 상태 전이를 직접 설계해야 할 때는 LangGraph의 `StateGraph`를 이용할 수 있다. LangSmith는 그 실행을 관찰하는 도구이며, 모델이나 대화 저장소를 대신하지 않는다. [LangChain 공식 개요](https://docs.langchain.com/oss/python/langchain/overview)

예를 들어 고객 상담 애플리케이션은 LangChain으로 문의 분류와 조회 기능을 연결하고, LangGraph로 대화 상태와 반복 실행을 관리하며, LangSmith로 잘못된 분류나 불필요한 Tool 호출을 확인할 수 있다.

## 2. Runnable: 조립을 가능하게 하는 실행 단위

Runnable은 입력을 받아 출력을 반환하는 공통 실행 인터페이스다. Prompt, Chat Model, Output Parser, Retriever 같은 구성 요소를 같은 호출 방식으로 다룰 수 있게 한다.

```text
Runnable A: 입력 → 출력
Runnable B: 입력 → 출력

A의 출력이 B가 요구하는 입력과 맞으면
A → B로 연결 가능
```

LCEL(LangChain Expression Language)은 이러한 실행 단위를 조합하는 표현 방식이다. 대표적으로 `|` 연산자는 앞 단계의 결과를 다음 단계에 전달한다.

```python
chain = prompt | model | parser
```

이 표현에서 가장 중요한 것은 **단계 사이의 데이터 계약**이다.

| 단계 | 대표 입력 | 대표 출력 |
|---|---|---|
| ChatPromptTemplate | 변수 Dictionary | 모델에 전달할 메시지를 담은 PromptValue |
| Chat Model | PromptValue 또는 메시지 | AIMessage |
| StrOutputParser | 모델 메시지 | 문자열 |
| 구조화 출력 모델 | 프롬프트 또는 메시지 | 지정한 Schema에 따른 객체 |
| Retriever | 검색 질문 | Document 목록 |

모두 Runnable이라고 해서 아무 순서로 연결할 수 있는 것은 아니다. 다음 단계가 `{"question": ...}`을 요구하는데 앞 단계가 문자열만 반환한다면 변환 단계가 필요하다. 모델을 교체할 때도 입력 형식뿐 아니라 Tool Calling과 구조화 출력 지원 여부를 확인해야 한다.

### invoke, stream, batch는 결과를 받는 방식이 다르다

| 호출 | 용도 | 주의할 점 |
|---|---|---|
| `invoke(input)` | 입력 하나의 최종 결과 받기 | 전체 작업이 끝날 때까지 기다림 |
| `stream(input)` | 생성되는 결과 조각을 순차적으로 받기 | 중간 단계가 스트리밍을 지원하지 않으면 전달이 지연될 수 있음 |
| `batch(inputs)` | 같은 실행 흐름에 여러 독립 입력 전달 | 동시성·요청 제한을 고려해야 함 |

스트리밍은 사용자에게 첫 응답을 빨리 보여주는 데 유용하다. 전체 계산량이나 최종 완료 시간이 반드시 줄어드는 것은 아니다. `batch()`도 공급자의 별도 Batch API 사용을 뜻하지는 않는다.

## 3. 기본 Chain: 작업 정의, 생성, 출력 변환의 분리

가장 기본적인 Chain은 Prompt, Model, Parser 세 단계로 구성된다.

```python
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.output_parsers import StrOutputParser
from langchain_openai import ChatOpenAI

prompt = ChatPromptTemplate.from_messages([
    ("system", "너는 기술 개념을 정확하고 쉽게 설명하는 교육 담당자다."),
    ("human", "{audience}에게 {concept}을 두 문장으로 설명해줘."),
])
model = ChatOpenAI(model="gpt-4o-mini", temperature=0.3)
chain = prompt | model | StrOutputParser()

answer = chain.invoke({
    "audience": "파이썬을 배우는 입문자",
    "concept": "검색 증강 생성",
})
```

Prompt는 작업의 목적과 입력 변수를 정의한다. Model은 그 메시지를 바탕으로 응답을 생성한다. Parser는 모델의 응답을 다음 코드에서 다루기 편한 형태로 변환한다.

이 분리 덕분에 설명 대상이나 문체는 Prompt에서, 사용하는 모델은 Model에서, 반환 형식은 Parser에서 바꿀 수 있다.

단, `StrOutputParser`는 답변의 사실성을 검증하지 않는다. 모델 메시지를 문자열로 바꾸는 역할이다. 잘못된 설명도 정상적인 문자열로 반환될 수 있으므로 출력 변환과 답변 평가는 별개다.

## 4. 구조화 출력: 자연어 판단을 프로그램의 데이터로 바꾸기

“배송 문제이며 긴급해 보입니다”라는 응답은 사람이 이해하기 쉽지만 프로그램의 조건문에서 쓰기에는 모호하다. 표현이 바뀔 때마다 문자열을 해석해야 하기 때문이다.

구조화 출력은 모델의 결과가 따라야 할 필드와 타입을 Schema로 정의하는 방식이다.

```python
from typing import Literal
from pydantic import BaseModel, Field

class Inquiry(BaseModel):
    category: Literal["배송", "환불", "결제", "기타"]
    urgency: Literal["low", "medium", "high"]
    summary: str = Field(description="문의의 핵심을 한 문장으로 요약")

classifier = model.with_structured_output(Inquiry)
result = classifier.invoke("같은 주문이 두 번 결제됐어요.")

if result.urgency == "high":
    route = "HUMAN_REVIEW"
else:
    route = "AUTO_REPLY"
```

Pydantic Schema를 사용하는 이 예제에서는 결과를 객체의 속성으로 읽을 수 있다. 구조화 출력의 구체적인 구현 방식은 모델·공급자에 따라 다르며, 응답 생성이나 검증이 실패하는 경우도 처리해야 한다. [모델의 구조화 출력](https://docs.langchain.com/oss/python/langchain/models#structured-output)

### 형식의 정확성과 판단의 정확성

`urgency`가 허용된 세 값 중 하나라는 사실은 형식적으로 유효하다는 뜻이다. 실제 긴급 문의를 `low`로 분류했다면 업무적으로는 틀린 결과다.

따라서 다음 세 요소를 함께 설계해야 한다.

1. **Schema**: 어떤 필드와 값이 허용되는가?
2. **분류 기준**: 어떤 상황을 긴급하다고 판단하는가?
3. **평가 사례**: 경계가 모호한 문의도 적절하게 분류하는가?

예를 들어 중복 결제, 배송 완료 후 미수령, 이전 환불 문의의 단순 요약 요청은 같은 기준으로 처리하면 안 된다. 이전 대화는 현재 문의를 해석하는 근거지만, 이전 턴의 긴급도를 무조건 물려받을 이유는 없다.

구조화 출력은 모델의 해석을 업무 로직과 연결하는 접점이다. 이후의 라우팅 규칙은 일반 Python 코드로 명시할 수 있다.

## 5. 대화 메모리: 이전 메시지를 다음 입력에 포함하기

일반적인 모델 호출은 전달받은 입력을 기준으로 응답한다. 애플리케이션이 이전 메시지를 보관하고 다시 전달해야 “아까 문의한 건” 같은 표현을 해석할 수 있다.

```text
첫 번째 요청
System + 현재 질문 → 답변
                       ↓
                  대화 이력 저장

두 번째 요청
System + 이전 질문·답변 + 현재 질문 → 답변
```

대화 메모리는 모델의 가중치를 바꾸는 학습이 아니다. **저장된 대화를 추론 시점의 문맥에 다시 넣는 과정**이다.

LCEL 예제에서는 `MessagesPlaceholder`가 이전 메시지가 들어갈 위치를 정하고, `RunnableWithMessageHistory`가 이력 저장과 주입을 연결한다. `session_id`는 어떤 이력을 사용할지 구분하는 키다.

Agent에서는 Checkpointer를 연결하고 `thread_id`로 대화 상태를 구분할 수 있다. 학습 코드의 `InMemorySaver`는 프로세스 메모리를 사용한다. 재시작 이후에도 상태를 유지하려면 영속 저장소를 사용하는 구성이 필요하다. [Agent의 단기 메모리](https://docs.langchain.com/oss/python/langchain/short-term-memory)

### 메모리를 설계할 때의 세 가지 경계

| 경계 | 확인할 내용 |
|---|---|
| 사용자 경계 | 서로 다른 사용자의 대화가 섞이지 않는가? |
| 수명 경계 | 프로세스 재시작 후에도 보존해야 하는가? |
| 문맥 크기 경계 | 이전 메시지 중 어떤 내용을 모델에 전달할 것인가? |

전체 이력을 매번 넣으면 토큰 비용과 지연이 증가하고 모델의 문맥 길이 제한에 도달할 수 있다. 최근 메시지 유지, 요약, 관련 이력 검색 등의 전략이 필요하다.

또한 이력을 저장하는 것과 모든 처리 단계가 그 이력을 참고하는 것은 다르다. 최종 답변 Chain에만 메모리를 연결했다면, 그 앞의 분류기나 주문번호 추출기는 여전히 현재 입력만 볼 수 있다. 후속 문의를 정확히 처리하려면 각 단계에 필요한 문맥을 명시적으로 전달해야 한다.

## 6. Tool Calling: 모델의 판단을 실제 기능에 연결하기

모델은 주문 상태를 그럴듯하게 설명할 수 있지만, 현재 주문 상태를 알려면 실제 데이터가 필요하다. Tool은 모델이 외부 조회나 계산 기능을 요청할 수 있도록 제공하는 인터페이스다.

Tool에는 일반적으로 이름, 설명, 입력 Schema, 실행 함수가 있다. 모델은 이 정보를 보고 사용할 도구와 인자를 생성한다.

```text
사용자: 주문 A1001의 배송 상태를 알려줘
  ↓
모델: get_order_status(order_id="A1001") 호출 요청
  ↓
애플리케이션: 함수와 인자 검증 → 실제 함수 실행
  ↓
Tool 결과: 배송 중
  ↓
모델: 조회 결과를 바탕으로 사용자에게 설명
```

`bind_tools()`는 모델에 도구의 명세를 제공한다. 함수 실행까지 자동으로 끝내는 메서드는 아니다. 직접 모델을 호출하는 구조에서는 `tool_calls`를 확인하고 함수를 실행한 뒤 결과를 `ToolMessage`로 전달하는 코드를 작성해야 한다. Agent를 사용하면 이 반복 실행을 프레임워크가 담당할 수 있다.

### 어떤 부분을 모델에 맡길 것인가

정형 주문번호 `A1001`은 정규식으로 추출할 수 있다. `A 1001`처럼 비정형 표현을 해석해야 할 때만 모델의 도움을 받을 수도 있다.

```text
규칙으로 추출 가능한가?
  ├─ 가능 → 추출 결과 검증 → 조회
  └─ 불가능 → 모델이 후보 제안 → 결과 검증 → 조회
```

형식 검증과 조회 권한 검증은 구분해야 한다. `A1001`이 올바른 형식이라고 해서 현재 사용자가 그 주문을 조회할 권한까지 갖는 것은 아니다. 권한과 실제 실행 여부는 애플리케이션이 결정해야 한다.

학습 코드의 주문 조회는 정해진 값을 반환하는 모의 함수다. 이를 실제 서비스로 확장하려면 주문 시스템 연동과 사용자별 접근 검증이 필요하다. 마찬가지로 “담당자에게 전달하겠습니다”라는 응답만 생성한 상태와 실제 업무 큐에 접수된 상태는 다르다.

## 7. 재시도와 Fallback: 실패했을 때의 실행 경로 설계

모델 API와 외부 검색은 네트워크 오류, 요청 제한, 일시적인 서비스 장애로 실패할 수 있다. 정상 경로뿐 아니라 실패 경로도 실행 흐름에 포함해야 한다.

| 전략 | 의미 | 적합한 상황 |
|---|---|---|
| Retry | 같은 작업을 다시 시도 | 일시적 연결 오류, 일시적 요청 제한 |
| Fallback | 다른 실행 경로로 전환 | 주 경로가 계속 실패하거나 사용 불가 |

다음은 두 전략의 조합을 보여주는 예시다. `primary`와 `backup`은 같은 입출력 계약을 가진 Runnable이라고 가정한다.

```python
safe_chain = primary.with_retry(
    stop_after_attempt=3
).with_fallbacks([backup])
```

여기서 `stop_after_attempt=3`은 최초 시도를 포함한 총 시도 횟수다. SDK의 `max_retries`처럼 추가 재시도 횟수를 나타내는 설정과 구분해야 한다. 여러 계층에 Retry가 있으면 실제 호출 횟수와 대기 시간이 예상보다 늘어날 수 있다.

잘못된 API 키나 존재하지 않는 모델명은 같은 요청을 반복해도 해결되지 않는다. 재시도할 예외와 중단할 예외를 구분하고, 전체 요청의 시간 제한도 고려해야 한다.

### Fallback도 같은 계약을 지켜야 한다

주 경로가 `Inquiry` 객체를 반환하는데 대체 경로가 문자열을 반환하면 뒤의 라우팅 코드가 실패할 수 있다. 대체 경로에서도 출력 Schema와 필요한 Tool 기능을 유지해야 한다.

또한 동일한 공급자와 모델을 두 번 생성했다고 독립적인 장애 대체 경로가 되는 것은 아니다. 학습 코드의 동일 모델 Fallback은 전환 구조를 보여주지만, 공급자 전체 장애를 해결하지는 못한다.

모델 전용 설정과 Runnable Wrapper의 적용 순서도 중요하다. 일반 Runnable로 감싼 뒤에는 `bind_tools()` 같은 모델 전용 메서드를 사용할 수 없는 경우가 있다. 사용하는 API가 요구하는 객체 타입을 확인하고, 모델 기능 설정과 실행 정책 적용을 분리해야 한다.

주문 취소나 결제처럼 상태를 바꾸는 Tool은 재시도로 중복 실행될 수 있다. 이런 작업에는 같은 요청을 여러 번 처리해도 결과가 중복되지 않도록 멱등성 키와 실행 기록 등을 설계해야 한다.

## 8. 복합 Chain: 순차 실행, 병렬 실행, 조건 분기

여러 모델 호출을 조립할 때는 데이터 의존 관계를 먼저 살펴봐야 한다.

### 순차 실행: 앞 단계의 결과가 필요한 경우

```text
문의 → 구조화 분류 → 긴급도 판단 → 응답 생성
```

응답 정책이 분류 결과에 의존하므로 분류가 먼저 끝나야 한다.

### 병렬 실행: 같은 입력을 독립적으로 분석하는 경우

```text
                  ┌→ 요약 ──────────┐
                  ├→ 감정 분석 ─────┤
댓글 입력 ────────┼→ 키워드 추출 ───┼→ 결과 결합
                  └→ 문의 분류 ─────┘
```

`RunnableParallel`은 동일한 입력을 여러 Runnable에 전달하고 각 출력을 이름별로 묶는다.

```python
analysis = RunnableParallel(
    summary=summary_chain,
    sentiment=sentiment_chain,
    keywords=keyword_chain,
)
```

각 작업의 시간이 `T1`, `T2`, `T3`이라면 순차 실행 시간은 대략 합에 가깝고, 충분한 동시 실행 여건에서 병렬 구간은 가장 느린 작업의 시간에 가까워진다. 실제로는 연결 수, 서버 대기, 요청 제한과 결과 결합 비용의 영향을 받는다.

병렬화는 호출 개수를 줄이지 않는다. 지연 시간을 줄일 수 있지만 동시에 보내는 요청과 토큰 사용량은 별도로 관리해야 한다.

### 조건 분기: 분석 결과를 처리 정책으로 연결하기

댓글 대응의 분기 규칙을 다음처럼 정의할 수 있다.

```text
negative 또는 urgency=high
  → 필요한 주문 상태 조회 → 담당자 확인 경로의 안내문 생성

그 외
  → 일반 자동 응답 생성
```

분기는 `RunnableBranch` 또는 일반 함수를 감싼 `RunnableLambda`로 구현할 수 있다. 현재 댓글 통합 코드에서는 `RunnableLambda` 안의 조건문을 사용한다.

이 구조에서는 모델이 감정과 긴급도를 해석하고, 코드는 그 값을 처리 정책에 연결한다. 모델 판단이 틀릴 가능성은 남아 있지만, 분류 이후 어떤 경로로 이동하는지는 코드로 확인할 수 있다.

감정 결과 역시 자유 문자열보다 `Literal["positive", "neutral", "negative"]` 같은 Schema로 제한하면 분기 계약이 명확해진다. 자연어로 특정 단어만 출력하라고 요청하는 것과 코드에서 그 형식을 검증하는 것은 다르다.

## 9. RAG: 답변을 만들기 전에 관련 근거 검색하기

RAG(Retrieval-Augmented Generation, 검색 증강 생성)는 외부 자료를 검색하고 그 결과를 모델의 입력에 포함해 답변을 생성하는 구조다. 모델이 학습 과정에서 접하지 못한 사내 규정이나 갱신된 문서를 활용하는 데 유용하다.

### 문서 준비와 질문 처리는 다른 단계다

```text
문서 준비 단계
원본 문서 → 읽기 → 필요한 단위로 분할 → Embedding → Vector Store

질문 처리 단계
질문 → Embedding → 관련 문서 검색 → 질문과 검색 결과로 Prompt 구성 → 답변
```

Embedding은 텍스트를 의미적 유사도를 비교할 수 있는 수치 벡터로 표현하는 과정이다. Vector Store는 이러한 벡터와 원문·메타데이터를 저장하고 검색하는 역할을 한다. Retriever는 질문에 관련된 Document를 가져오는 인터페이스다.

긴 문서는 적절한 크기로 분할해야 하지만, 학습 코드처럼 이미 짧은 `Document` 목록을 준비했다면 별도 분할 없이 임베딩할 수도 있다. 분할의 목적은 무조건 글자 수를 줄이는 것이 아니라 답변에 필요한 의미 단위를 검색할 수 있게 만드는 데 있다.

### 검색 결과를 생성 단계의 입력으로 바꾸기

```python
rag_chain = (
    RunnableParallel(
        context=retriever | format_docs,
        question=RunnablePassthrough(),
    )
    | prompt
    | model
    | StrOutputParser()
)
```

질문 하나가 두 경로로 전달된다. `context` 경로에서는 관련 문서를 검색하고 문자열로 정리한다. `question` 경로에서는 원래 질문을 유지한다. 두 값이 Prompt의 변수에 들어가므로 모델은 질문과 근거를 함께 읽는다.

### 검색 성공과 답변 가능 여부는 다르다

`k=3`은 검색 결과를 최대 세 개 가져오겠다는 설정이지, 세 개 모두 답변의 근거라는 뜻이 아니다. 자료에 없는 질문도 상대적으로 가까운 문서를 반환할 수 있다.

따라서 RAG는 다음을 따로 평가해야 한다.

| 평가 대상 | 질문 |
|---|---|
| 검색 품질 | 답변에 필요한 문서를 가져왔는가? |
| 생성 품질 | 검색된 문서에 근거해 답했는가? |
| 답변 보류 | 근거가 없을 때 없다고 답하는가? |
| 출처 | 답변의 근거 문서를 다시 확인할 수 있는가? |

문서에 없는 해외 출장비를 질문했는데 병가 규정이 검색됐다고 가정해 보자. 이때 적절한 답변은 출장비를 추측하는 것이 아니라 현재 자료에서 확인할 수 없다고 알리는 것이다.

RAG는 모델을 재학습하지 않으며 사실성을 자동 보장하지도 않는다. 문서 갱신, 검색 품질, 출처 보존과 답변 평가가 함께 필요하다. 검색 문서에 포함된 명령문도 시스템 지침과 구분해 데이터로 다뤄야 한다.

## 10. Agent: 다음 작업을 모델이 선택하는 실행 구조

고정된 Chain은 개발자가 실행 경로를 정한다. Agent는 목표와 현재까지의 실행 결과를 바탕으로 모델이 다음 Tool과 인자를 선택한다.

```text
사용자 요청
  ↓
모델 판단 ── Tool 호출 없음 ──→ 최종 답변
  │
  └─ Tool 호출 요청 → Tool 실행 → 결과를 모델에 전달
                         ↑                  │
                         └── 다음 호출 ─────┘
```

예를 들어 “서울 날씨를 확인하고 야외 행사 규정도 알려줘”라는 요청은 날씨 조회와 문서 검색을 함께 요구한다. Agent는 등록된 Tool을 선택하고 결과를 종합할 수 있다.

```python
from langchain.agents import create_agent
from langgraph.checkpoint.memory import InMemorySaver

agent = create_agent(
    model=model,
    tools=[get_weather, search_docs],
    checkpointer=InMemorySaver(),
)

result = agent.invoke(
    {"messages": [{"role": "user", "content": "서울 날씨와 야외 행사 규정을 알려줘."}]},
    config={"configurable": {"thread_id": "event-planning-01"}},
)
```

이 코드에서는 등록된 두 Tool이 정의되어 있다고 가정한다. Tool을 여러 번 호출하는 Agent 하나와 여러 Agent가 협력하는 구조는 다르다. **복수 Tool 사용이 곧 멀티 Agent를 의미하지는 않는다.**

### Chain과 Agent는 누가 실행 경로를 결정하는가로 구분한다

| 기준 | 고정 Workflow·Chain | Agent |
|---|---|---|
| 경로 결정 | 개발자가 정한 연결과 조건 | 모델의 판단과 실행 결과 |
| 적합한 문제 | 알려진 순서의 분류·검증·처리 | 요청에 따라 필요한 작업이 달라지는 문제 |
| 장점 | 경로와 비용을 예측하기 쉬움 | 다양한 요청을 유연하게 조합 |
| 관리할 점 | 분기 증가, 입력 변화 대응 | 잘못된 Tool 선택, 반복 호출, 비용 변동 |

공식 문서도 Workflow의 사전 정의된 경로와 Agent의 동적인 작업 선택을 구분한다. [Workflows and agents](https://docs.langchain.com/oss/python/langgraph/workflows-agents)

“기온이 특정 값 이상일 때만 문서를 검색해”라는 프롬프트는 모델이 해석하는 지침이다. 그 조건을 반드시 지켜야 한다면 온도를 구조화한 뒤 코드의 조건문이나 Graph Edge로 검사해야 한다. 자연어 지침과 실행을 강제하는 제어 구조는 서로 다른 역할을 한다.

## 11. LangGraph: 상태와 실행 전이를 명시하기

LangGraph는 실행 단계를 Node로, 단계 사이의 이동을 Edge로, 공유 데이터를 State로 표현한다.

| 구성 요소 | 의미 |
|---|---|
| State | 현재까지의 메시지, 조회 결과 등 실행 데이터 |
| Node | State를 읽고 업데이트를 반환하는 작업 |
| Edge | 다음에 실행할 Node로의 연결 |
| Conditional Edge | 현재 상태에 따라 다음 경로를 선택하는 연결 |
| Checkpointer | 실행 상태를 저장하고 이어가는 데 사용하는 구성 요소 |

Tool Calling Agent의 기본 반복 구조는 다음처럼 표현할 수 있다.

```text
START → agent
          ├─ tool_calls 있음 → tools → agent
          └─ tool_calls 없음 → END
```

`agent` Node는 모델을 호출하고, `tools` Node는 요청된 도구를 실행한다. Tool 결과가 State에 추가되면 모델이 그 결과를 읽고 다음 행동을 결정한다.

메시지 State의 `add_messages` 같은 Reducer는 Node가 반환한 메시지를 기존 상태와 어떻게 합칠지 정의한다. 단순한 전체 덮어쓰기와 구분해야 하며, 메시지 ID가 같으면 기존 메시지를 갱신하는 동작도 지원한다.

직접 작성한 Graph는 기본 반복 구조를 명시적으로 보여준다. 그렇다고 `create_agent()`가 제공하는 모든 기능을 몇 개의 Node만으로 재현한 것은 아니다. 승인 대기, 오류 복구, 종료 조건 등 필요한 정책을 추가로 설계해야 한다.

Checkpointer가 있다고 어떤 장애에서도 자동으로 복구되는 것도 아니다. 저장소의 영속성, 재개 방식과 외부 작업의 중복 실행 여부까지 함께 고려해야 한다.

## 12. 통합 구조: Agent 안에 검증된 Chain을 Tool로 넣기

앞의 블록들은 하나의 서비스에서 함께 사용할 수 있다. 유용한 구성은 상위 Agent가 기능을 선택하고, 각 기능 내부는 목적이 분명한 Chain으로 구현하는 방식이다.

```text
사용자 / Gradio
       ↓
통합 Agent + 대화 상태
       ├─ FAQ Tool
       │    → 문의 분류 → 긴급도 분기 → 응답
       ├─ 댓글 Tool
       │    → 병렬 분석 → 처리 경로 결정 → 주문 조회 → 응답
       ├─ 문서 검색 Tool
       │    → Retriever → 관련 문서 반환
       └─ 날씨 Tool
            → 외부 검색 → 조회 결과 반환
       ↓
Tool 결과를 바탕으로 최종 답변
```

이 구조에서는 Agent가 모든 세부 절차를 즉석에서 만들 필요가 없다. 댓글 처리처럼 이미 정해진 절차는 Tool 내부에 두고, 상위 Agent는 어떤 기능이 필요한지 선택한다.

고정 RAG Chain은 검색 후 생성까지 자체적으로 수행한다. 반면 검색 기능만 Tool로 노출하면 상위 Agent가 검색 결과를 받고 최종 답변을 생성할 수 있다. 생성 단계가 어디에 있는지에 따라 모델 호출 수와 책임이 달라진다.

### 통합할수록 상태의 소유권이 중요하다

상위 Agent의 `thread_id`와 내부 댓글 Chain의 `session_id`는 자동으로 같은 값이 되지 않는다. 별도의 저장소를 쓰는 경우에는 어느 계층이 어떤 대화 이력을 보관하는지 정해야 한다.

예를 들어 댓글 문자열의 해시를 세션 키로 만들면 같은 댓글은 같은 키를 사용한다. 이는 사용자별 대화 격리와 다르다. 실제 서비스에서는 인증된 사용자와 대화 식별자를 필요한 하위 단계까지 전달해야 한다.

### Gradio는 사용자 인터페이스 계층이다

Gradio는 입력창과 대화 화면을 제공하고 사용자의 요청을 실행 함수에 연결한다. 탭을 FAQ, 댓글, 문서 검색으로 나눴다고 Agent의 도구 선택이 강제되는 것은 아니다. 탭은 사용 안내이고, 강제 라우팅이 필요하면 서버 코드에서 경로를 결정해야 한다.

UI를 바꾸더라도 동일한 실행 함수를 재사용하면 터미널과 웹 화면에서 같은 로직을 검증할 수 있다. 화면의 대화 기록을 지울 때 서버의 세션 상태도 어떻게 처리할지 함께 설계해야 한다.

## 13. LangSmith: 최종 답변 뒤의 실행 경로 확인하기

최종 답변만으로는 어떤 프롬프트가 들어갔는지, 검색이 수행됐는지, Tool이 몇 번 호출됐는지 알기 어렵다.

LangSmith에서 Run은 모델 호출이나 Tool 실행 같은 개별 작업을 나타낸다. Trace는 하나의 작업을 처리하면서 발생한 Run들을 연결한 실행 기록이다. [LangSmith 관찰성 개념](https://docs.langchain.com/langsmith/observability-concepts)

```text
요청 Trace
  ├─ 문의 분류
  │    └─ 모델 호출
  ├─ 주문 상태 조회
  │    └─ Tool 입력과 결과
  └─ 답변 생성
       └─ 모델 입력 메시지와 출력
```

학습 코드에서 트레이스를 읽을 때는 다음 질문이 유용하다.

| 확인 대상 | 확인할 내용 |
|---|---|
| Prompt | 변수 치환 후 모델에 실제 전달된 메시지가 의도와 맞는가? |
| Memory | 이전 사용자·AI 메시지가 모델 입력에 들어갔는가? |
| 구조화 출력 | 분류 값과 긴급도가 다음 분기와 연결됐는가? |
| Tool | 호출된 이름과 인자, 반환 결과가 적절한가? |
| RAG | 가져온 문서에 답변의 근거가 있는가? |
| 실행 시간 | 병렬 작업이 겹쳐 실행되는가? 어느 단계가 느린가? |

트레이스의 성공 표시는 예외 없이 실행이 끝났다는 신호다. 정책을 올바르게 해석했는지, 답변이 사실인지까지 보장하지는 않는다. 기대 결과가 있는 사례를 준비해 분류·검색·답변 품질을 평가해야 한다.

공유할 트레이스에는 입력 문장과 Tool 결과에 포함된 개인정보나 내부 정보가 없는지도 확인해야 한다. 관찰 데이터 역시 애플리케이션 데이터의 일부다.

## 14. 블록을 연결할 때 확인해야 할 설계 기준

기능을 추가할 때마다 “이전 단계에서 무엇을 받고, 다음 단계에 무엇을 보낼 것인가”를 확인하면 오류의 위치를 좁힐 수 있다.

| 증상 | 확인할 경계 | 개선 방향 |
|---|---|---|
| Prompt 변수 오류 | 이전 출력과 Prompt 입력 | 변수 이름과 Dictionary 구조 맞추기 |
| 구조화 결과를 이력에 저장하지 못함 | Schema 객체와 메시지 형식 | 대화 메시지와 분석 결과를 분리하거나 명시적으로 변환 |
| Tool 명세를 연결했지만 조회가 안 됨 | 호출 요청과 함수 실행 | 실행 루프와 Tool 결과 전달 확인 |
| 사용자 간 대화가 섞임 | 세션 식별과 저장소 | 사용자·대화별 식별자와 접근 제어 적용 |
| RAG가 없는 정보를 답함 | 검색 결과와 생성 근거 | 검색 품질, 보류 기준과 출처 확인 |
| 응답이 느리고 호출 수가 많음 | 중첩 Chain·Agent·Retry | Trace로 실제 호출 경로와 재시도 횟수 측정 |
| 필수 조건을 Agent가 무시함 | 모델 지침과 실행 제어 | 필수 조건을 코드 분기나 Graph로 구현 |

좋은 조립 구조는 각 블록의 책임을 설명할 수 있는 구조다. Prompt는 작업을 정의하고, Schema는 데이터 형식을 정하며, Memory는 맥락을 제공한다. Tool은 외부 기능을 실행하고, RAG는 근거를 공급한다. Chain과 Agent는 그 기능의 실행 경로를 구성하며, Trace는 실제 실행을 확인하게 한다.

모델에 맡길 해석과 코드로 보장할 규칙을 구분하면 작은 Chain부터 통합 Agent까지 같은 기준으로 설계할 수 있다.
