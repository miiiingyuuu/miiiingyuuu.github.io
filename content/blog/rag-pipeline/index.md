# RAG와 배터리 수명 예측 이해 — 검색·근거·피처·일반화로 보는 데이터 파이프라인

문서를 읽고 질문에 답하는 RAG와 초기 배터리 신호로 수명을 예측하는 회귀 모델은 결과의 형태가 다르다. 하나는 자연어 답변을 만들고, 다른 하나는 숫자를 예측한다. 그러나 둘 다 원본 데이터를 모델이 사용할 수 있는 정보로 바꾸고, 그 결과가 새로운 상황에서도 유효한지 확인해야 한다.

문서 검색 결과가 질문과 비슷하다는 이유만으로 답변의 근거가 되는 것은 아니다. 배터리 피처가 수명과 강하게 상관된다는 이유만으로 다른 배치에서도 잘 예측하는 것도 아니다. **데이터 표현, 정보의 사용 범위, 평가 기준을 함께 설계해야 모델의 결과를 해석할 수 있다.**

이 글은 RAG Pipeline과 배터리 수명 예측에 필요한 기술을 두 축으로 정리한다. 첫 번째 축은 문서에서 근거를 찾아 답변하는 방법이고, 두 번째 축은 관측 데이터에서 피처를 만들어 일반화 성능을 평가하는 방법이다.

| 구분 | RAG | 배터리 수명 예측 |
|---|---|---|
| 원본 | PDF·웹 문서 | 셀별 실험·사이클·시계열 데이터 |
| 모델 입력 표현 | 청크·임베딩·검색 문맥 | 초기 사이클의 통계 피처 |
| 출력 | 근거를 포함한 답변 | 총 Cycle Life 예측값 |
| 핵심 평가 | 검색 적합성·근거 충실도·답변 정확성 | 예측 오차·배치 간 일반화 |
| 주요 실패 | 근거 누락·잘못된 검색·근거 밖의 주장 | 데이터 누수·외삽·분포 차이 |

> 코드 예시는 개념 설명을 위한 축약이다. 배터리 실험의 수치는 별도로 수행한 미니프로젝트의 결과이며, 논문의 동일 조건 재현이나 현장 ESS 성능을 뜻하지 않는다.

## 1. RAG: 외부 지식을 모델의 입력에 연결하기

RAG는 Retrieval-Augmented Generation, 검색 증강 생성이다. 질문에 관련된 외부 정보를 찾고, 그 정보를 질문과 함께 모델에 전달해 답변을 생성한다.

```text
질문
  → 관련 문서 검색
  → 질문 + 검색 문맥 + 답변 지침
  → LLM
  → 답변과 출처
```

일반적인 RAG 요청에서는 검색 결과를 제공할 때 LLM의 가중치를 바꾸지 않는다. 문서가 프롬프트의 문맥으로 들어간다. 반면 Fine-tuning은 학습을 통해 모델의 파라미터를 조정한다. 특정 업무의 출력 형식·행동을 학습시키는 목적과 외부 근거를 조회하는 목적은 구분할 필요가 있으며, 두 방법을 함께 사용할 수도 있다.

원래 RAG 논문은 검색기와 생성 모델을 결합하는 학습 구조를 제안했다. 오늘날의 문서 질의응답 시스템에서는 이미 학습된 모델에 검색 문맥을 공급하는 형태도 널리 사용한다. 따라서 “RAG는 어떤 모델도 학습하지 않는다”라고 일반화하면 부정확하다. [RAG 원논문](https://arxiv.org/abs/2005.11401)

검색 대상은 벡터 저장소에 한정되지 않는다. 관계형 데이터베이스, 검색 엔진, 내부 API의 결과도 답변의 근거로 사용할 수 있다. 이 글에서는 PDF·웹 문서를 처리하는 검색 파이프라인을 중심으로 설명한다.

## 2. 문서 색인과 질문 처리는 실행 시점이 다르다

RAG는 문서를 준비하는 과정과 사용자의 질문을 처리하는 과정으로 나눌 수 있다.

```text
문서 준비·색인
원본 문서 → 내용 추출 → 청크 분할 → 임베딩 → 검색 인덱스

질문 처리
질문 → 검색 질의 구성 → 후보 검색 → 재정렬
     → 문맥 구성 → 답변 생성 → 근거 확인
```

문서 준비는 문서가 추가되거나 변경될 때 수행하고, 질문 처리는 요청마다 수행한다. 이렇게 분리하면 매 질문마다 전체 PDF를 다시 읽고 임베딩하는 비용을 피할 수 있다. 문서 내용이 바뀌었는데 인덱스가 갱신되지 않으면 오래된 내용으로 답변하게 되므로 문서와 인덱스의 버전도 함께 관리해야 한다.

LangChain의 Loader, Text Splitter, Embedding, Vector Store, Retriever는 이 과정의 서로 다른 역할을 맡는다. 기능을 연결할 때는 각 단계가 어떤 데이터를 받아 어떤 데이터를 반환하는지 확인해야 한다. [공식 Retrieval 설명](https://docs.langchain.com/oss/python/deepagents/retrieval)

## 3. Document Loading: 텍스트와 문서 구조를 함께 보존하기

Loader는 PDF·웹 페이지 등에서 내용을 읽어 문서 객체로 만든다. 문서 객체에는 본문과 함께 파일명, 페이지, URL 같은 메타데이터를 담을 수 있다.

```python
# 설명용 문서 표현
document = {
    "page_content": "특정 조건에서만 적용되는 설비 점검 기준...",
    "metadata": {
        "source": "equipment-guide.pdf",
        "page": 12,
        "document_version": "2026-09",
    },
}
```

이 정보는 출처 표시뿐 아니라 문서 버전 필터링, 검색 결과 중복 제거, 오류 추적에 사용된다. 페이지 번호가 0부터 시작하는 내부 값인지 사람이 읽는 번호인지도 명확히 해야 한다.

PDF에서 추출된 텍스트의 순서가 사람이 읽는 순서와 항상 같지는 않다. 다단 편집, 표, 머리말과 꼬리말 때문에 서로 다른 문장이 섞일 수 있다. 스캔 문서는 OCR이 필요할 수 있고, 표는 숫자뿐 아니라 행·열의 관계와 단위를 유지해야 한다.

예를 들어 “정격 출력 100kW”에서 단위가 사라지면 검색이 성공해도 답변이 틀릴 수 있다. 문서가 표 중심인지, 스캔 이미지인지, 일반 텍스트인지에 따라 파싱 방식을 선택해야 한다. 검색 문제를 임베딩 모델 교체만으로 해결할 수 없는 이유다.

## 4. Chunking: 검색 단위와 설명에 필요한 문맥의 균형

청크는 문서를 검색 가능한 작은 조각으로 나눈 단위다. 너무 큰 청크는 여러 주제가 섞여 질문과의 대응이 흐려지고, 너무 작은 청크는 조건·예외·정의가 잘려 의미를 잃을 수 있다.

| 설정 | 기대 효과 | 부담 또는 위험 |
|---|---|---|
| 작은 청크 | 세부 내용 검색 | 문맥·조건 누락 |
| 큰 청크 | 주변 설명 보존 | 불필요한 내용과 토큰 증가 |
| 청크 간 Overlap | 경계에서 잘린 내용 보완 | 중복 검색·저장 비용 증가 |
| 제목·문단 기반 분할 | 문서 구조 유지 | 원본 구조의 품질에 의존 |

`RecursiveCharacterTextSplitter`는 문단·줄·공백 등의 경계를 순서대로 활용한다. 기본 길이 계산이 문자 수라면 `chunk_size=1000`은 1,000토큰을 뜻하지 않는다. 토큰 기준 분할과 문자 기준 분할은 구분해야 한다. Overlap도 경계 손실을 완화하는 목표값이며, 모든 청크가 같은 크기로 정확히 겹친다는 의미는 아니다. [Recursive Text Splitter 문서](https://docs.langchain.com/oss/python/integrations/splitters/recursive_text_splitter)

적절한 크기는 문서의 내용과 질문 유형에 따라 달라진다. 용어 정의를 찾는 질문과 여러 조항을 종합하는 질문은 필요한 문맥이 다르다. 청크 설정은 검색 점수와 최종 답변의 근거 보존을 함께 확인하며 선택해야 한다.

## 5. Embedding과 Vector Search: 의미를 비교할 수 있는 표현

임베딩은 텍스트를 숫자 벡터로 변환하는 방법이다. 질문과 문서를 호환되는 표현 공간에 놓으면 벡터의 거리나 유사도로 후보를 찾을 수 있다.

```text
질문: "배터리 건강 상태는 어떻게 확인하는가?"
문서: "SOH는 초기 용량 대비 현재 용량의 비율이다."

표현은 다르지만 의미가 관련됨
  → 임베딩 기반 검색의 후보가 될 수 있음
```

코사인 유사도는 두 벡터의 방향을 비교한다.

$$
\operatorname{cos}(q,d)=\frac{q\cdot d}{\|q\|\|d\|}
$$

그러나 모든 벡터 검색이 코사인 유사도를 쓰는 것은 아니다. 인덱스와 설정에 따라 내적 또는 유클리드 거리를 사용할 수 있으며, 반환 점수가 클수록 좋은지 작을수록 좋은지도 다르다. 유사도 0.9를 “정답일 확률 90%”로 읽어서는 안 된다.

문서 임베딩과 질문 임베딩은 같은 모델 또는 서로 호환되도록 설계된 모델로 생성해야 한다. 벡터 차원이 같아도 다른 모델의 표현 공간이 호환된다고 보장할 수 없다. 모델을 바꿀 때는 문서의 재임베딩과 인덱스 갱신 여부를 확인해야 한다.

FAISS는 벡터 인덱싱·검색을 위한 라이브러리이고, Chroma는 임베딩과 문서·메타데이터를 관리하며 검색하는 저장소다. 어느 도구를 쓰더라도 **벡터 저장·검색 성공과 답변 근거 확보는 별도로 확인해야 한다.** [FAISS 공식 설명](https://faiss.ai/), [Chroma 공식 설명](https://docs.trychroma.com/)

## 6. BM25와 Hybrid Search: 정확한 표현과 의미 검색 결합

의미 검색은 표현이 다른 문장을 찾는 데 유용하지만 제품 코드, 약어, 고유명사 같은 정확한 문자열을 놓칠 수 있다. BM25는 질의의 단어가 문서에 어떻게 나타나는지를 이용하는 대표적인 어휘 검색 방식이다.

BM25는 단어의 등장 빈도뿐 아니라 흔한 단어인지, 문서가 얼마나 긴지 등을 고려한다. 같은 단어가 반복될수록 점수가 무한히 선형 증가하는 방식은 아니다. 한국어에서는 조사·어미가 붙은 표현을 어떤 토큰으로 나누는지도 검색 결과에 영향을 준다. [BM25 공식 설명](https://www.elastic.co/docs/reference/elasticsearch/index-settings/similarity)

| 검색 방식 | 찾기 유리한 정보 | 약점 |
|---|---|---|
| BM25 | 모델명·규정 번호·정확한 용어 | 표현이 다른 문장의 대응 |
| Dense Search | 유사한 의미·다른 표현 | 드문 문자열·정확한 코드 |
| Hybrid Search | 두 방식의 후보를 함께 활용 | 결합 규칙과 비용 설계 필요 |

두 검색기의 점수는 척도가 다르므로 단순히 더하면 한쪽이 과도하게 지배할 수 있다. 순위 기반 결합의 한 예인 Reciprocal Rank Fusion은 문서가 각 검색 결과에서 몇 번째에 나타났는지를 이용한다.

$$
\operatorname{RRF}(d)=\sum_{j}\frac{w_j}{c+\operatorname{rank}_j(d)}
$$

여기서 $w_j$는 검색기별 가중치이고, $c$는 최상위 순위의 영향력을 조절하는 상수다. 문서가 나타난 검색 결과에 대해서만 더하며, 같은 문서는 ID 등으로 묶어야 한다. 위 식은 원래 RRF에 가중치를 적용한 형태다. Hybrid라는 이름 자체가 성능 향상을 보장하지는 않으며 동일한 평가 질문에서 비교해야 한다. [RRF 원논문 정보](https://research.google/pubs/reciprocal-rank-fusion-outperforms-condorcet-and-individual-rank-learning-methods/)

## 7. Reranking과 Context Compression: 후보에서 근거로 좁히기

첫 검색은 관련 문서를 빠뜨리지 않도록 후보를 넓게 찾고, 재정렬은 그 후보를 질문에 맞게 다시 평가하는 역할을 맡는다.

```text
넓은 후보 검색: 문서 30개
  → 질문과 후보의 적합성 재평가
  → 최종 문맥: 문서 5개
```

Bi-encoder는 질문과 문서를 각각 벡터화해 비교한다. Cross-encoder 기반 Reranker는 질문과 문서를 함께 입력해 적합성을 계산한다. 질문·문서 쌍마다 계산하므로 대규모 전체 검색보다 후보 재정렬에 사용하기 적합하다. [Retrieve & Re-Rank 설명](https://sbert.net/examples/sentence_transformer/applications/retrieve_rerank/README.html)

재정렬은 입력 후보에 없는 정답 문서를 새로 찾지 못한다. 정답 문서가 첫 검색에서 누락됐다면 후보 검색부터 고쳐야 한다. 반대로 후보에는 있지만 최종 문맥에서 탈락한다면 재정렬이나 문맥 선택을 살펴봐야 한다.

Context Compression은 검색된 문서에서 질문과 관계있는 내용을 추리거나 불필요한 부분을 줄인다. 이때 “단, 특정 조건에서는 적용하지 않는다” 같은 예외를 지우면 의미가 바뀐다. 압축 결과도 출처와 대응되어야 하며, 토큰 수 감소만으로 품질을 판단할 수 없다.

## 8. Query Rewriting과 다양한 검색 전략

사용자의 질문에는 생략된 주어나 이전 대화의 지시어가 포함될 수 있다. Query Rewriting은 원래 질문을 검색에 적합한 형태로 바꾸는 방법이다.

```text
이전 대화: 배터리 SOH 기준 설명
현재 질문: "그 기준을 넘으면 어떻게 해?"
검색 질의: "배터리 SOH 기준 초과 시 점검 및 조치"
```

질의 재작성은 질문의 의도를 보존해야 한다. 제품명·날짜·수치 조건을 임의로 바꾸면 검색 범위가 달라진다. 원래 질문과 재작성된 질의를 함께 기록하면 오류를 확인하기 쉽다.

| 전략 | 해결하려는 문제 |
|---|---|
| MultiQuery | 표현 차이로 놓친 후보를 여러 검색 질의로 보완 |
| ParentDocument | 작은 청크로 검색하고 더 큰 부모 문맥을 반환 |
| Metadata Filter | 버전·문서 종류 등 명시적 조건으로 대상 제한 |
| MMR | 서로 비슷한 결과만 반복되는 현상 완화 |

질의를 늘리면 호출 수와 검색 비용이 증가한다. 부모 문서를 반환하면 검색 단위와 답변 문맥 단위가 달라진다. 청크별 평가를 하는 경우, 부모 문서가 반환됐다는 이유만으로 정확한 근거 청크를 찾았다고 간주하지 않도록 평가 단위를 정해야 한다.

## 9. 검색 평가와 답변 평가는 다른 것을 측정한다

검색기는 답변에 필요한 근거를 찾는지 평가하고, 생성 모델은 그 근거로 질문에 올바르게 답하는지 평가한다. 두 단계의 지표를 나누면 실패 지점을 구분할 수 있다.

| 지표 | 확인하는 내용 |
|---|---|
| Hit Rate@k | 정답 근거가 상위 k개 결과에 하나라도 들어왔는가? |
| Recall@k | 정답 근거 여러 개 중 얼마나 찾았는가? |
| Precision@k | 반환 결과 중 관련 근거의 비중은 얼마인가? |
| MRR@k | 첫 정답 근거가 얼마나 높은 순위에 있는가? |

질문 $N$개에 대한 MRR@k는 첫 관련 결과의 순위 $r_i$를 이용해 계산한다. 상위 k개에 관련 결과가 없으면 해당 항은 0이다.

$$
\operatorname{MRR@k}=\frac{1}{N}\sum_{i=1}^{N}\frac{1}{r_i}
$$

예를 들어 3개 질문에서 첫 정답의 순위가 1위, 2위, 검색 실패라면 MRR은 $(1+1/2+0)/3=0.5$다. 정답 근거가 여러 개 필요한 질문에서는 첫 정답만 보는 MRR과 전체 근거 회수율을 함께 볼 필요가 있다.

정답 근거 ID를 명시한 평가와 단어 겹침으로 관련성을 추정하는 평가는 엄밀성이 다르다. 키워드가 겹쳐도 틀린 문서일 수 있고, 표현이 달라도 올바른 문서일 수 있다. 자동 생성 질문만 평가하면 실제 사용자의 모호한 질문에 대한 성능을 과대평가할 수도 있다.

## 10. Groundedness, Faithfulness와 답변 정확성

Groundedness와 Faithfulness는 구현에 따라 세부 정의가 다르지만, 여기서는 답변의 주장이 제공된 문맥으로 뒷받침되는지를 뜻한다. Faithfulness의 한 측정 방식은 답변을 주장으로 나눈 뒤 근거가 확인되는 주장 비율을 구하는 것이다. [Ragas Faithfulness 정의](https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/faithfulness/)

```text
검색 문서에 "검사 주기는 6개월"이라고 적혀 있음
답변도 "검사 주기는 6개월"이라고 설명함

문맥에 대한 충실도: 높을 수 있음
실제 최신 기준에 대한 정확성: 문서의 최신성 확인 필요
```

근거 충실도, 질문 관련성, 실제 사실 정확성은 서로 다르다. 오래된 문서에 충실하게 답하면 근거 평가는 통과하더라도 현재 기준에는 틀릴 수 있다. 출처 번호를 붙였다는 사실만으로 그 출처가 해당 주장을 뒷받침하는 것도 아니다.

LLM을 평가자로 쓰면 많은 답변을 비교할 수 있지만, 그 점수도 모델의 판단이다. 평가 Prompt, 모델 버전, 기준 문서와 정답의 품질이 결과에 영향을 준다. 중요한 사례는 사람이 근거와 답변을 대조하고, 개발에 사용하지 않은 질문에서도 평가해야 한다.

답변 생성에는 근거가 부족할 때 보류하거나 추가 질문을 하는 경로가 필요하다. 프롬프트에 “모르면 모른다고 답하라”를 적는 것만으로 이 동작이 보장되지는 않는다. 검색 결과의 충분성 확인과 실제 실패 사례 평가가 함께 필요하다.

## 11. LangGraph: 상태와 분기로 검색 흐름을 제어하기

검색과 생성이 한 번씩 실행되는 흐름은 고정 Chain으로 구성할 수 있다. 검색 결과에 따라 재검색·다른 정보원 조회·답변 보류가 필요하면 상태와 분기를 명시적으로 관리해야 한다.

| 구성 요소 | 역할 | 예시 |
|---|---|---|
| State | 현재 실행의 데이터 | 질문·검색 문서·답변·재시도 횟수 |
| Node | 상태를 받아 작업하고 갱신값 반환 | 검색·근거 평가·생성 |
| Edge | 다음 작업 연결 | 검색 → 평가 |
| Conditional Edge | 판단에 따른 경로 선택 | 생성 또는 재검색 |
| Reducer | 같은 상태 필드의 갱신 방식 | 교체 또는 누적 |

LangGraph의 노드는 반드시 LLM 호출일 필요가 없다. 일반 Python 함수로 검색 결과를 정리하거나 반복 횟수를 확인할 수도 있다. 상태 필드에 누적이 필요한지 최신 값으로 교체해야 하는지를 구분하지 않으면, 오래된 문서가 남거나 같은 문서가 반복해서 쌓일 수 있다. [Graph API 설명](https://docs.langchain.com/oss/python/langgraph/graph-api)

```text
검색 → 근거 평가
         ├─ 충분함 → 생성 → 답변 검증 → 종료
         └─ 부족함 → 질의 수정 → 재검색
                                └─ 예산 초과 → 보류
```

무한 재검색을 막기 위해 최대 재시도 횟수, 시간, 호출 비용과 종료 조건을 정해야 한다. 그래프의 recursion limit는 실행의 super-step 제한이며, 서비스의 재검색 횟수·비용 제한을 자동으로 대신하지 않는다.

## 12. Self, Corrective, Adaptive, Agentic RAG의 구분

이 이름들은 검색을 어떻게 결정하고 실패에 어떻게 대응하는지를 설명할 때 사용한다.

| 패턴 | 중심 판단 |
|---|---|
| Self-RAG 스타일 | 검색 결과·생성 답변의 근거와 적합성을 재검토 |
| Corrective RAG 스타일 | 검색 결과가 부족하거나 부적절하면 보완 경로 실행 |
| Adaptive RAG 스타일 | 질문의 성격에 맞는 정보원·검색 경로 선택 |
| Agentic RAG | 모델이 검색 도구 호출과 추가 작업을 동적으로 선택 |

예를 들어 내부 규정 질문은 내부 문서로, 최근 뉴스 질문은 웹 검색으로 보내는 분기를 설계할 수 있다. 다만 웹 검색 결과도 발행일·출처·본문을 확인해야 하며 검색 결과의 요약만으로 사실을 확정할 수 없다.

학습용 그래프에서 LLM 평가자와 조건부 분기를 구성한 것은 원논문의 학습 방법을 그대로 구현했다는 의미가 아니다. 원래 [Self-RAG 논문](https://arxiv.org/abs/2310.11511)은 reflection token을 포함한 학습·생성 방법을 다루고, [CRAG 논문](https://arxiv.org/abs/2401.15884)은 검색 평가와 보정 구조를 제안한다. 여기서는 그 아이디어와 연결되는 실행 패턴을 구분한다.

Agentic이라는 이름이 정확성을 보장하지는 않는다. 자유롭게 도구를 선택할수록 실행 경로와 비용의 변동도 커지므로 검색 품질·답변 품질·지연 시간·실패 경로를 함께 평가해야 한다.

## 13. 배터리 예측: 먼저 관측 단위와 Target을 정하기

배터리 데이터에는 수명, 용량, 전압, 전류, 온도처럼 서로 다른 층위의 값이 들어 있다. 예측 문제를 정의하려면 “어떤 단위의 무엇을, 언제 확보한 정보로 예측하는가”를 먼저 정해야 한다.

| 개념 | 의미 |
|---|---|
| ESS | 전기를 저장했다가 필요한 시점에 공급하는 시스템 |
| SOC | 정의한 최대 충전 가능량 대비 현재 충전량 비율 |
| SOH | 초기·기준 성능 대비 현재 건강 상태; 여기서는 용량 기준 |
| EOL | 미리 정한 성능 기준에 도달한 수명 종료 시점 |
| Cycle Life | 정해진 EOL까지의 총 사이클 수 |
| RUL | 현재 시점부터 EOL까지 남은 수명 |
| C-rate | 정격 용량에 대한 충·방전 전류의 비율 |

정격 용량이 1Ah인 셀에서 1A는 1C다. 이상적인 계산에서 1C는 한 시간에 정격 용량을 충전하는 속도에 대응하지만, 실제 충전 시간은 CC-CV 과정, 종료 기준과 손실 등에 영향을 받는다. 따라서 C-rate만으로 실제 충전 시간을 확정할 수 없다.

초기 100사이클로 총 Cycle Life를 예측하는 문제와 현재 SOH를 추정하는 문제는 Target이 다르다. 같은 사이클 좌표와 EOL 정의를 사용한다면 남은 사이클 수를 총수명에서 현재 사이클 수를 빼서 표현할 수 있지만, 현재 프로젝트의 출력은 총수명이다. 이를 곧바로 남은 날짜나 팩 교체 시점으로 바꿀 수는 없다.

Cycle Life 회귀와 장·단수명 분류도 목적이 다르다. EDA에서 사용한 수명 구간과 분류 모델의 임계값은 별도로 정의해야 한다. 구간을 선택하는 기준이 바뀌면 라벨과 지표도 바뀐다.

## 14. 계층 데이터: 시계열 포인트 수와 학습 표본 수는 다르다

배터리 데이터는 보통 다음 구조를 가진다.

```text
Batch
  └─ Cell
      ├─ Descriptors: 수명·충전 정책
      ├─ Summary: 사이클별 QD·온도·충전시간
      └─ Cycles: 한 사이클 내부의 시간·전압·전류·용량
```

수명을 셀 단위로 예측한다면 학습 행 하나는 셀 하나에 대응한다. 셀당 수천 개의 사이클과 전압 포인트가 있다고 해서 독립적인 수명 표본도 수천 개가 되는 것은 아니다. 작은 셀 집합에 고차원 곡선을 그대로 넣으면 과적합 위험이 크다.

원저자 데이터 설명은 descriptors, summary, cycle 정보를 구분하며 `Qdlin`을 전압 축에 선형 보간한 방전 용량으로 설명한다. 파일에 따라 MATLAB 구조체와 Python의 중첩 Dictionary처럼 저장 표현도 다르다. [원저자 데이터 설명](https://github.com/rdbraatz/data-driven-prediction-of-battery-cycle-life-before-capacity-degradation)

MATLAB v7.3 형식처럼 HDF5를 사용하는 파일은 `h5py`로 접근할 수 있다. 이때 숫자 배열을 읽는 것과 다른 Dataset을 가리키는 참조를 따라가는 것은 다르다. 배열 축, 참조 구조, 실제 사이클 번호를 확인해야 잘못된 신호를 피처로 만들지 않는다.

## 15. EDA: 모델 선택 이전에 데이터의 조건을 확인하기

EDA는 그래프를 나열하는 작업보다 넓다. 데이터의 분포와 품질을 확인하고, 어떤 변수·분할·모델이 적절할지 판단하는 과정이다.

| 확인 대상 | 모델 설계와의 연결 |
|---|---|
| 수명 분포·장단수명 비율 | 학습 범위와 평가 범위 차이 |
| 용량 열화 곡선 | 추세·비선형성·요약 피처 후보 |
| 초기 ΔQ(V) | 초기 신호의 구분력 |
| 충전 정책·온도·전류 | 조건 차이와 그룹 구조 |
| 상관·피처 간 중복 | 피처 선택·규제 모델 후보 |
| 결측·측정 이상 | 입력 처리와 평가 분모 |

배치마다 같은 축과 구간으로 분포를 비교하면 범위 차이를 읽기 쉽다. 절대 기준으로 단수명 셀이 없는 배치는 해당 그룹 비교가 불가능하므로, 배치 내 사분위 그룹 같은 보조 분석을 사용할 수 있다. 다만 상대 수명 그룹을 절대 장·단수명 그룹처럼 표현해서는 안 된다.

정답 라벨 결측과 관측 종료도 구분해야 한다. 실험이 끝났다는 사실이 EOL에 도달했다는 뜻은 아닐 수 있다. 종료 사유가 확인되지 않은 데이터를 마지막 관측 사이클로 라벨링하면 다른 문제의 정답을 만들 수 있다. EOL에 도달하기 전에 관측이 끝났다는 사실을 확인한 경우에는 right censoring을 다루는 생존 분석이 후속 후보가 될 수 있지만, 모든 결측을 검열로 단정해서는 안 된다.

이상치도 자동으로 지울 대상은 아니다. 센서 오류, 기록 오류, 드문 정상 셀, 중요한 고위험 셀은 서로 다른 경우다. 삭제 근거와 적용 범위를 구분하고, 원본을 유지한 결과와 학습 데이터 내 처리의 민감도를 비교해야 한다.

## 16. 열화 곡선과 Knee Point: 설명용 정보와 예측 입력의 구분

방전 용량 $Q_D(n)$은 사이클 $n$에서 사용할 수 있는 용량을 나타낸다. 초기에는 용량이 증가하거나 불규칙하게 움직일 수 있고, 이후 감소가 더 빨라지는 구간이 나타날 수 있다.

Knee Point는 열화가 급격해지는 전환 구간을 탐색하는 개념이다. 평활한 곡선에 구간 선형 모델을 맞춰 전·후 기울기와 적합 오차를 비교하는 방법 등을 사용할 수 있다. 그러나 평활 창, 후보 범위와 적합 기준에 따라 위치가 바뀌므로 탐색 결과를 화학적 전이의 확정점으로 읽으면 안 된다.

```text
전체 수명 곡선으로 추정한 Knee
  → 이미 관측한 열화를 설명하는 정보

100사이클 시점에서 확보한 초기 기울기
  → 초기 예측의 입력 후보
```

전체 수명 이후에 확인한 Knee를 초기 수명 예측의 X에 넣으면 미래 정보가 들어간다. 초기 관측 창 안에서 별도로 정의한 변화점 피처와 전 수명에서 계산한 Knee는 서로 다른 변수다. 물리적으로 의미 있는 변수도 예측 시점에 알 수 없으면 사용할 수 없다.

## 17. ΔQ(V): 곡선을 비교해 초기 열화 신호 만들기

전압별 방전 용량 곡선의 차이는 다음처럼 정의할 수 있다.

$$
\Delta Q(V)=Q_{100}(V)-Q_{10}(V)
$$

이는 100번째와 10번째 사이클의 곡선을 **같은 전압 지점에서** 비교하는 것이다. Summary의 `QD100-QD10`처럼 사이클별 스칼라 용량 두 개를 뺀 값과 구분해야 한다.

| 변수 | 의미 |
|---|---|
| QD | 한 사이클을 요약한 방전 용량 |
| Qdlin | 전압 축에 맞춰 보간한 방전 용량 곡선 |
| QD100−QD10 | 두 사이클의 스칼라 용량 차이 |
| ΔQ(V) | 두 곡선의 전압별 차이 |

전압 축의 길이뿐 아니라 지점·순서·단위가 일치해야 한다. 서로 다른 전압 범위나 기준에서 추출한 배열을 위치만 맞춰 빼면 의미 없는 차이가 된다. 1부터 시작하는 사이클 번호와 Python의 0부터 시작하는 위치도 구분해야 한다.

실제 데이터의 전압 범위가 안내 문서와 다르면 파일의 축을 확인하고 사용 범위를 기록해야 한다. 미니프로젝트의 파일에서는 2.0~3.5V의 1,000개 지점을 사용했으며, 이 범위를 모든 배터리 데이터의 공통값으로 일반화하지 않는다.

## 18. 곡선의 분산을 피처로 만드는 이유

ΔQ(V)의 분산은 전압별 변화가 평균 주변에서 얼마나 달라지는지를 요약한다. 변화량의 평균과 변화 형태의 퍼짐은 다른 정보를 담는다.

$$
\mu_{\Delta Q}=\frac{1}{m}\sum_{j=1}^{m}\Delta Q(V_j)
$$

$$
\operatorname{Var}(\Delta Q)=\frac{1}{m}\sum_{j=1}^{m}
\left(\Delta Q(V_j)-\mu_{\Delta Q}\right)^2
$$

여기서 분산은 **한 셀의 전압 지점 사이에서 계산한 기술적 분산**이다. 셀 사이의 수명 분산이 아니다. 위 식은 전체 곡선 지점을 요약하는 $ddof=0$ 정의다.

분산 값의 크기 차이가 매우 크면 로그 변환으로 범위를 압축할 수 있다.

```python
import numpy as np

def delta_capacity_features(q10, q100):
    """동일 전압 축으로 정렬된 유한한 1차원 배열을 입력으로 가정한다."""
    delta = np.asarray(q100) - np.asarray(q10)
    return {
        "dq_mean": float(delta.mean()),
        "dq_min": float(delta.min()),
        "dq_logvar": float(np.log10(max(delta.var(ddof=0), 1e-12))),
    }
```

작은 양수는 로그 0을 피하기 위한 계산상의 하한이다. 값을 크게 고르면 아주 작은 분산의 차이를 지울 수 있으므로 처리 기준을 기록해야 한다. 분산의 단위는 용량이 Ah라면 Ah²이며, 피처의 단위와 전압 범위도 고정해야 한다.

분산은 모든 지점에 같은 상수를 더해도 변하지 않는다. 따라서 일정한 용량 기준점 차이에 대한 민감도를 확인하는 데 도움이 된다. 그러나 전압 축의 이동, 측정 절차 변경, 비상수 왜곡까지 해결하는 것은 아니다. 분산이 크다는 사실만으로 정확한 열화 원인이나 특정 전압에서의 변화를 확정할 수도 없다.

초기 방전 곡선의 통계값을 수명 예측에 연결하는 연구 배경은 [Severson 등의 배터리 수명 예측 논문](https://www.nature.com/articles/s41560-019-0356-8)에서 확인할 수 있다.

## 19. Feature Engineering: 의미·중복·관측 시점 검토

피처 엔지니어링은 원본 데이터를 모델에 적합한 입력으로 바꾸는 과정이다. 배터리의 초기 용량 기울기, 평균 온도, 충전시간 중앙값, 충전 정책의 C-rate 등을 후보로 만들 수 있다.

상관계수는 선형 관계의 강도를 요약하지만 인과효과나 외부 예측 성능을 보장하지 않는다. 충전 전류와 수명의 관계에는 온도, 충전 전환 조건, 셀·측정 환경이 함께 작용할 수 있다. 배치별 관계의 방향이 달라지는지도 확인해야 한다.

다중공선성은 여러 피처가 강하게 중복되는 상황이다. 평균·최고·최저 온도를 모두 넣었을 때 정보가 크게 늘지 않으면서 회귀계수의 안정성이 낮아질 수 있다. 대표 변수 선택, 중복 피처 대체, Ridge 규제 같은 방법을 비교할 수 있다.

피처를 추가하면 학습 오차는 줄어들기 쉽지만, 작은 데이터에서는 검증 오차가 커질 수도 있다. “많은 정보를 넣었으니 더 좋은 모델”이라는 결론 대신 같은 분할에서 피처 세트를 비교해야 한다.

## 20. Data Leakage: 예측 시점과 평가 경계를 넘는 정보

데이터 누수는 실제 예측 시점에 사용할 수 없거나 평가 과정에서 분리되어야 하는 정보를 학습에 사용해 성능을 왜곡하는 문제다.

| 누수 또는 평가 오염 사례 | 문제 |
|---|---|
| 최종 용량·총 관측 길이를 초기 피처로 사용 | 미래 정보 포함 |
| 전체 데이터로 중앙값·Scaler를 계산 | 평가 데이터의 분포를 학습에 사용 |
| 동일 셀의 사이클 행을 양쪽에 분할 | 같은 대상의 정보가 학습·평가에 공유 |
| 테스트 점수를 보며 모델·제외 규칙 변경 | 테스트셋이 개발 데이터로 사용됨 |

일반적인 전처리는 학습셋에서 `fit()`하고 평가셋에서는 `transform()`만 수행한다. 결측 보완처럼 정답을 직접 쓰지 않는 처리도 평가 데이터 전체에서 계산하면 검증 경계를 넘을 수 있다. [scikit-learn의 누수 설명](https://scikit-learn.org/stable/common_pitfalls.html)

상관을 보고 피처를 고르는 과정에도 라벨이 사용된다. 외부 배치 라벨을 EDA에서 확인했다면, 모델 선택을 학습 배치 안에서만 했더라도 완전한 blind test라고 주장할 수 없다. 이 경우 평가 결과는 여전히 유용하지만 해석상의 한계를 밝혀야 한다.

## 21. Group Split과 Cross-Validation: 독립성에 맞는 분할

분할은 모델이 어떤 새로운 대상을 맞혀야 하는지를 표현한다. 새로운 셀, 새로운 충전 정책, 새로운 실험 배치에 대한 일반화는 서로 다른 평가 목표다.

| 분할 기준 | 주로 평가하는 대상 |
|---|---|
| 셀 단위 분할 | 새로운 셀 |
| 정책 Group Split | 학습에 없던 정책 그룹 |
| 배치 단위 분할 | 다른 수집 조건·실험 배치 |
| 시간 단위 분할 | 이후 시점의 관측 |

같은 정책의 셀이 양쪽에 들어가는 것이 모든 문제에서 자동으로 Target 누수는 아니다. 다만 그룹 내 조건이 유사하고 새로운 정책에 대한 성능이 목적이라면, 정책을 공유한 무작위 분할이 낙관적인 평가를 만들 수 있다. 평가 목적에 맞는 그룹 분리가 필요하다.

`GroupKFold`는 각 fold에서 같은 그룹이 학습과 검증에 겹치지 않게 분할한다. 그룹별 셀 수가 다르면 fold의 크기도 달라질 수 있으며, 그룹 중복이 없다는 사실이 모든 관측의 통계적 독립성을 증명하는 것은 아니다. [GroupKFold 문서](https://scikit-learn.org/stable/modules/generated/sklearn.model_selection.GroupKFold.html)

CV는 개발 데이터 안에서 후보를 비교하는 데 사용하고, Hold-out은 선택한 후보의 성능을 별도로 확인하는 데 사용할 수 있다. Hold-out 결과를 반복해서 보고 설계를 바꾸면 독립성은 약해진다. Batch 2·3 같은 외부 평가셋도 튜닝 데이터로 재사용하지 않아야 한다. [교차검증 설명](https://scikit-learn.org/stable/modules/cross_validation.html)

## 22. Pipeline: 전처리와 모델을 같은 검증 단위로 묶기

Pipeline은 결측 보완, 표준화, 모델 학습을 하나의 추정기로 연결한다. 이를 CV의 각 학습 fold에서 fit하면 fold마다 전처리 통계도 새로 계산된다.

```python
from sklearn.impute import SimpleImputer
from sklearn.linear_model import Ridge
from sklearn.pipeline import Pipeline
from sklearn.preprocessing import StandardScaler

model = Pipeline([
    ("imputer", SimpleImputer(strategy="median")),
    ("scaler", StandardScaler()),
    ("regressor", Ridge(alpha=1.0)),
])

# 이미 분리한 학습·검증 데이터라는 가정
model.fit(X_train, y_train)
y_pred = model.predict(X_valid)
```

이 구조는 평가셋에 학습셋과 같은 전처리를 적용하고, 전처리 객체와 모델을 함께 저장하는 데 유용하다. 다만 Pipeline 밖에서 전체 데이터 기반 피처 선택을 했다면 그 누수까지 자동으로 막아주지는 않는다. [Pipeline 문서](https://scikit-learn.org/stable/modules/generated/sklearn.pipeline.Pipeline.html)

표준화는 피처의 척도를 맞춘다. 특히 Ridge처럼 계수 크기에 벌점을 주는 모델에서는 단위 차이가 규제 강도에 영향을 주기 때문에 중요하다. 반대로 모든 모델에서 표준화가 필수이거나 표준화만 하면 배치 차이가 사라진다고 볼 수는 없다.

## 23. Baseline, Linear Regression, Ridge와 Target 변환

Baseline은 복잡한 모델이 단순한 기준보다 나은지 확인하는 비교 대상이다. 학습 라벨의 중앙값을 항상 예측하는 Dummy 모델도 기준이 된다. 선형회귀는 피처와 Target의 관계를 선형 함수로 표현한다.

$$
\hat y=\beta_0+\sum_{j=1}^{p}\beta_jx_j
$$

Ridge는 잔차 제곱합에 계수 크기의 벌점을 더한다.

$$
\min_{\beta_0,\beta}
\sum_i(y_i-\beta_0-x_i^T\beta)^2+\alpha\sum_j\beta_j^2
$$

$\alpha$는 규제 강도를 조절한다. 규제는 계수의 변동을 줄이는 데 도움이 될 수 있지만, 학습에 없는 수명 구간이나 측정 방식 차이를 자동으로 해결하지 않는다. [선형 모델 설명](https://scikit-learn.org/stable/modules/linear_model.html)

양수 Target에 로그 변환을 적용하면 큰 값의 영향을 줄이고 다른 관계 형태를 표현할 수 있다. `z=log10(y)`로 학습했다면 예측도 `y_hat=10**z_hat`으로 역변환한 뒤 원래 수명 단위에서 평가해야 한다. `TransformedTargetRegressor`는 변환·역변환을 추정기와 함께 관리한다. [Target 변환 문서](https://scikit-learn.org/stable/modules/generated/sklearn.compose.TransformedTargetRegressor.html)

로그 공간의 제곱오차를 줄이는 것이 원 단위 MAPE를 직접 최소화하는 것과 같지는 않다. 또한 로그 공간 예측을 역변환한 값이 원 단위의 조건부 평균이라고 자동으로 해석할 수도 없다. Target 변환은 실제 사용할 지표에서 비교해야 한다.

## 24. 1-SE Rule과 작은 데이터의 모델 선택

CV 평균이 가장 작은 후보가 항상 안정적인 선택은 아니다. 작은 표본에서는 fold 구성에 따라 점수가 바뀌고, 후보를 많이 비교할수록 우연히 좋은 후보를 선택할 위험도 커진다.

1-SE Rule은 최소 평균 오차의 후보와 비슷한 범위에 있는 모델 중 더 단순한 후보를 고르는 선택 규칙이다. 실험에서는 다음 상한을 사용했다.

$$
\text{허용 상한}=\overline{E}_{best}+\frac{s_{best}}{\sqrt{K}}
$$

$s_{best}$는 최저 평균 후보의 fold 오차 표준편차이고 $K$는 fold 수다. 상한 안의 후보에서 피처 수·모델 복잡도 등을 사전에 정한 우선순위로 비교한다. 여기서 “단순함”의 정의와 동점 처리 기준도 선택 규칙의 일부다.

배터리 실험에서 최저 평균 후보는 로그 Target 선형회귀였지만, 원 Target 선형회귀도 허용 범위 안에 있었다. 정해진 우선순위에 따라 단일 피처의 원 Target 모델을 선택했다. 이는 로그 모델이 통계적으로 열등하다는 증명은 아니다.

CV fold는 학습 데이터를 공유하므로 $s/\sqrt{K}$를 엄밀한 독립 표본의 표준오차나 신뢰구간처럼 해석해서는 안 된다. 이 실험에서는 단순한 후보를 선택하기 위한 근사 규칙으로 사용했으며, 선택된 CV 점수 자체도 독립적인 최종 평가 점수는 아니다.

## 25. MAPE, MAE, RMSE와 Gap을 함께 읽기

MAPE는 정답 대비 절대 오차의 비율을 평균한다.

$$
\operatorname{MAPE}(\%)=\frac{100}{N}\sum_i\frac{|\hat y_i-y_i|}{|y_i|}
$$

| 지표 | 표현 | 주요 관점 |
|---|---|---|
| MAPE | % | 정답 대비 상대 오차 |
| MAE | Target과 같은 단위 | 평균 절대 오차 |
| RMSE | Target과 같은 단위 | 큰 오차에 더 큰 비중 |
| R² | 무차원 | 정답 변동 대비 예측 오차 |

같은 100사이클 오차도 실제 수명 400회에서는 25%, 2,000회에서는 5%다. MAPE는 단수명 셀의 같은 절대 오차를 더 크게 반영한다. 정답이 0에 가깝다면 상대 오차가 폭증하고, 0에서는 일반적인 식이 정의되지 않으므로 Target의 특성을 확인해야 한다. scikit-learn의 함수는 20%를 `0.2`로 반환하므로 백분율 표에서는 100을 곱한다. [MAPE API 문서](https://scikit-learn.org/stable/modules/generated/sklearn.metrics.mean_absolute_percentage_error.html)

미니프로젝트의 결과는 다음과 같았다.

| 평가 | MAPE |
|---|---|
| B1 개발 데이터의 정책 그룹 CV 평균 | 7.201% |
| B1 독립 Hold-out | 13.144% |
| B2 외부 평가 | 31.529% |
| B3 추가 외부 평가 | 12.591% |

Hold-out과 B2의 차이는 `31.529−13.144=18.385%p`다. 논문 비교 목표 9.1% 대비 B2 차이는 `22.429%p`다. 두 비율의 단순 차이는 백분율포인트이며, 상대적인 오차 증가율과 다르다. 이 비교는 동일한 데이터 처리·분할 조건의 논문 재현을 뜻하지 않는다.

fold 크기가 다르면 fold MAPE의 단순 평균과 모든 OOF 예측을 합친 MAPE도 다를 수 있다. 어느 집계 방식을 보고했는지 명시해야 한다. CV·Hold-out 차이가 크다고 바로 과적합을 확정하기보다 선택 편향, 그룹 구성과 작은 표본의 영향도 살펴봐야 한다.

## 26. Batch Shift와 일반화: 높은 상관이 충분하지 않은 이유

일반화는 학습에 사용하지 않은 데이터에서 성능이 유지되는 능력이다. 외부 배치에서는 피처 분포뿐 아니라 수명 분포와 피처·수명의 관계도 달라질 수 있다.

| 차이 | 설명 |
|---|---|
| 입력 분포 차이 | $P(X)$가 달라짐 |
| Target 분포 차이 | $P(y)$가 달라짐 |
| 관계 차이 | $P(y\mid X)$가 달라짐 |
| 측정 조건 차이 | 같은 이름의 변수라도 수집·가공 기준이 달라짐 |

이 차이는 동시에 나타날 수 있다. Target 분포가 다르다는 사실만으로 통계적 의미의 label shift가 확정되는 것은 아니며, 외부 오차 증가만으로 원인이 식별되는 것도 아니다.

배터리 실험의 B1에는 500회 미만 셀이 없었지만 B2의 유효 라벨 39셀 중 28셀이 그 구간에 있었다. B3에는 B1의 최대 수명을 넘어서는 장수명 셀이 있었다. 학습에서 보지 못한 구간으로 예측하는 외삽 문제가 발생할 수 있는 조건이다.

B2 단수명 셀은 모두 과대 예측됐고, B3 장수명 셀은 모두 과소 예측됐다. 이 결과는 개발 표본의 수명 범위 부족을 중요한 원인 후보로 만든다. 그러나 일부 큰 오차는 입력 피처 범위 안에서도 나타났으므로 범위 이탈만으로 실패를 설명할 수 없다. 측정 조건과 조건부 관계의 차이도 추가로 확인해야 한다.

## 27. 오류 분석을 도메인의 비용에 연결하기

평균 지표만 보면 어떤 셀에서 어떤 방향으로 틀렸는지 알기 어렵다. 실제 값과 예측값의 차이인 잔차를 구간별로 나누면 실패 패턴을 확인할 수 있다.

$$
\text{잔차}=\hat y-y
$$

| 오차 방향 | 수명 예측의 의미 | ESS 관점의 위험 |
|---|---|---|
| 양수 | 실제보다 오래 사용할 것으로 예측 | 점검·교체가 늦어질 가능성 |
| 음수 | 실제보다 빨리 종료될 것으로 예측 | 불필요한 조기 교체 비용 |

두 오차의 비용은 같지 않다. MAPE가 낮더라도 위험한 과대 예측이 집중되면 교체 판단에 바로 사용하기 어렵다. 수명 구간·충전 정책·측정 조건별 오차와 불확실성을 함께 확인해야 한다.

실험실 단일 셀의 사이클 수와 현장 ESS 팩의 수명도 다르다. 팩에서는 셀 편차, 열관리, SOC 운용 구간, 달력 열화와 센서 품질이 함께 작용한다. 초기 예측을 점검 우선순위의 보조 정보로 사용하는 것과 자동 교체 기준으로 사용하는 것은 요구되는 검증 수준이 다르다.

## 28. RAG와 DS에 공통으로 필요한 재현성과 관찰성

재현성은 결과를 같은 조건에서 다시 확인할 수 있게 하는 성질이다. 관찰성은 실제 실행에서 어떤 입력과 경로가 결과를 만들었는지 추적하는 능력이다.

| 관리 대상 | RAG | DS |
|---|---|---|
| 원본 버전 | 문서·URL·개정일 | 데이터 파일·라벨 |
| 변환 기준 | Parser·청크·임베딩 | 피처 정의·결측 보완·Scaler |
| 실행 설정 | 검색 k·재정렬·Prompt·모델 | 분할·Seed·후보·규제 강도 |
| 중간 기록 | 질의·검색 문서·평가·도구 호출 | fold·전처리 통계·OOF 예측 |
| 결과 검증 | 주장과 출처 대조 | 저장 모델 예측·지표 재계산 |

RAG는 LLM API의 모델 버전이나 검색 대상의 변화로 같은 입력에서도 결과가 달라질 수 있다. DS도 Seed만 고정했다고 환경·데이터·연산 차이까지 모두 제거되는 것은 아니다. 라이브러리 버전, 데이터 해시와 설정을 함께 기록해야 한다.

노트북의 출력이 남아 있다는 사실은 현재 환경에서 실행 가능하다는 보증이 아니다. 깨끗한 커널에서 위에서 아래로 전체 실행하고, 저장된 모델을 새 프로세스에서 복원해 같은 입력의 예측을 비교하는 검증이 필요하다. RAG에서는 호출 성공 여부뿐 아니라 검색 문서와 답변의 실제 대응을 확인해야 한다.

운영 중에는 RAG의 문서 버전·미응답률·근거 없는 주장과 DS의 입력 품질·피처 분포·신규 라벨 오차를 각각 추적할 수 있다. 입력 분포 변화는 품질 저하의 경보이며 성능 저하의 확정 증거는 아니다. 배터리 EOL처럼 정답이 늦게 확보되는 경우에는 입력 경보와 성능 평가의 시점도 달라진다.

결국 새로운 문서나 새로운 실험 배치에서도 결과가 유효한지 확인하려면, 모델의 마지막 출력만 보아서는 부족하다. 원본이 어떻게 표현됐는지, 어떤 정보가 허용됐는지, 어느 데이터로 선택하고 평가했는지 설명할 수 있어야 한다. 이 경계를 명확히 만드는 것이 검색 시스템과 예측 모델을 신뢰할 수 있는 파이프라인으로 연결하는 기반이다.
