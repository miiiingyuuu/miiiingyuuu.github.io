## 왜 이 글을 읽었나

추천 시스템에서 A/B 테스트 대신 MAB를 쓰는 경우를 공부하다가 무신사 테크블로그 글을 발견했습니다. 실제 커머스 서비스에서 MAB를 어떻게 도입하고, 데이터 파이프라인을 어떻게 구성했는지 구체적으로 나와 있어서 이론과 실제를 함께 이해하기 좋은 글이었습니다.

## 1. 문제 상황 — 고정 정렬의 한계

무신사 스토어에는 배너, 태그, 브랜드 등 페이지마다 수많은 정보가 배치되어 있습니다. 문제는 화면에 노출할 수 있는 공간은 제한적인데 제공할 수 있는 정보의 양은 훨씬 많다는 것입니다.

기존 방식은 인기 브랜드를 **고정된 순서**로 노출했습니다. 이 방식에는 명확한 한계가 있었습니다.

```
기존 고정 정렬의 문제:
- 상위 노출 브랜드로 트래픽이 집중
- 하위 브랜드는 노출 기회 자체가 없음
- 사용자 반응이 좋더라도 순위가 바뀌지 않음
- 시간대나 트렌드 변화에 유연하게 대응 불가
```

이 문제를 해결하기 위해 도입한 것이 **MAB(Multi-Armed Bandit) 알고리즘** 기반의 실시간 정렬 시스템입니다.

---

## 2. MAB(Multi-Armed Bandit)란?

### 슬롯머신 비유

MAB는 슬롯머신(one-armed bandit)에서 유래한 이름입니다. 여러 대의 슬롯머신이 있고 각각의 당첨 확률이 다를 때, 제한된 시도 안에서 **최대한 많은 보상을 얻으려면 어떻게 해야 하는가**를 다루는 문제입니다.

커머스에 대입하면 이렇습니다.

```
슬롯머신 → 브랜드 / 배너 / 상품 (각각 하나의 "팔(Arm)")
손잡이를 당기는 행위 → 해당 아이템을 상위에 노출
보상(Reward) → 클릭, 구매 등의 사용자 반응
목표 → 클릭률(CTR)을 최대화하는 정렬 순서 찾기
```

### Exploration vs Exploitation 트레이드오프

MAB의 핵심 개념은 이 두 가지 사이의 균형입니다.

**Exploration (탐색)**
아직 충분히 시도하지 않은 아이템을 노출해봅니다. 성과가 낮아 보이더라도 기회를 줍니다. 새로운 정보를 수집합니다.

**Exploitation (활용/수확)**
지금까지 쌓인 데이터를 기반으로 가장 성과가 좋은 아이템을 집중 노출합니다. 현재 알고 있는 최선을 선택합니다.

```
극단적 Exploration만 하면:
  좋은 아이템을 알면서도 새것만 시도 → 기회 손실

극단적 Exploitation만 하면:
  초기 데이터가 적을 때 잘못된 판단으로 고착 → 좋은 아이템을 놓침

→ 둘 사이의 적절한 균형이 필요
```

## 3. MAB 주요 알고리즘 비교

### ε-Greedy (입실론 그리디)

가장 단순하고 직관적인 방법입니다.

```
(1-ε)의 확률 → Exploitation: 지금까지 성과가 가장 좋은 아이템 선택
  ε의 확률 → Exploration: 랜덤으로 아이템 선택

ε = 0.1 이면 10%의 확률로 탐색, 90%는 현재 최선 선택
```

장점은 구현이 간단하다는 것이고, 단점은 시도 횟수나 불확실성을 고려하지 않아 탐색 비율이 항상 일정하다는 것입니다.

### UCB (Upper Confidence Bound)

ε-Greedy의 단점을 보완한 알고리즘입니다. 시도 횟수가 적을수록 더 높은 점수를 부여해 탐색 기회를 늘립니다.

```
선택 기준 = 현재 평균 성과 + 불확실성 보정값

불확실성 보정값 = c × √(ln(전체 시도 수) / 해당 아이템 시도 수)
→ 시도 횟수가 적을수록 보정값이 커짐 → 더 자주 선택됨
```

무신사는 UCB의 경우 확률이 아닌 연산 후 최고값만 선택(Exploitation)하게 되어 환경적 요인이 반영되기 어렵다고 판단해 채택하지 않았습니다.

### Thompson Sampling

구글 애널리틱스에서도 활용할 만큼 좋은 성능으로 알려진 **확률적 알고리즘**입니다. 무신사가 최종 선택한 방법이기도 합니다.

```
핵심 아이디어:
1. 각 아이템의 성공/실패 이력을 Beta 분포로 모델링
2. 매 결정마다 각 분포에서 샘플을 하나씩 추출
3. 샘플값이 가장 높은 아이템을 선택

→ 불확실한 아이템일수록 분포가 넓어짐
→ 넓은 분포에서는 높은 값이 샘플링될 확률도 높아짐
→ 자연스럽게 탐색(Exploration)이 유도됨
```

늦게 들어오는 피드백도 수용할 수 있고, 확률 기반으로 탐색과 활용을 자연스럽게 분배합니다.

#### Beta 분포와 성공/실패 카운트

```python
# 각 아이템마다 성공(클릭)과 실패(미클릭)를 누적
alpha = 클릭 수 + 1    # 성공 횟수
beta  = 미클릭 수 + 1  # 실패 횟수

# Beta(alpha, beta) 분포에서 샘플링
import numpy as np
score = np.random.beta(alpha, beta)

# 가장 높은 score가 나온 아이템을 선택
```

## 4. 시스템 아키텍처 — 어떻게 구현했는가

### 전체 데이터 흐름

```
사용자 행동 (클릭, 노출, 페이지뷰)
        ↓
Apache Kafka (실시간 스트리밍)
        ↓
Apache Druid (시계열 데이터 저장 + 집계)
        ↓
MAB 알고리즘 (Thompson Sampling 적용)
        ↓
정렬 점수 계산
        ↓
브랜드/배너/태그 노출 순서 결정
```

### Apache Kafka의 역할

Kafka는 사용자의 실시간 행동 데이터(페이지뷰, 노출 수, 클릭 수)를 수집하는 **데이터 스트리밍 플랫폼**입니다. MAB 정렬의 기반이 되는 실시간 데이터를 이 Kafka에서 스트리밍합니다.

### Apache Druid를 선택한 이유

MAB에 적용하기 위해서는 시간 기준으로 집계된 데이터를 별도로 저장해야 합니다. 이를 위해 **시계열 데이터 저장소**가 필요했고, Elasticsearch와 Apache Druid 두 가지를 후보로 검토했습니다.

최종적으로 **Apache Druid**를 선택했는데, 무신사가 꼽은 Druid의 장점은 다음과 같습니다.

```
웹 콘솔을 통해 데이터 스트림과 SQL을 조회하고 세그먼트 관리 가능

롤업(Rollup) 기능:
  로그 데이터를 시간 단위(day, hour, minute, second, none)와
  필드 단위로 집계하여 필요한 데이터로 함축 저장 가능

클러스터 구성:
  Master  → 메타데이터 관리 + 코디네이터
  Data    → 스트림 데이터 인덱싱 + 세그먼트 관리
  Query   → 데이터 질의응답 + 웹 콘솔 지원
```

롤업이 특히 중요한 이유는 MAB가 "특정 기간 동안의 클릭 수 / 노출 수"를 필요로 하기 때문입니다. 로우 데이터를 그대로 쌓으면 용량이 폭발하지만, 시간 단위로 집계해서 저장하면 훨씬 효율적으로 관리할 수 있습니다.

### MAB 적용 5단계

원글에서 소개한 MAB 적용 과정을 단계별로 정리하면 이렇습니다.

```
1단계: Kafka에서 실시간 사용자 행동 데이터 스트리밍

2단계: Druid에서 시간 단위로 데이터 집계 저장
        (노출 수, 클릭 수를 기간별로 롤업)

3단계: Druid 데이터 기반으로 Thompson Sampling 적용
        - 각 아이템의 alpha(클릭), beta(미클릭) 계산
        - Beta 분포에서 샘플링

4단계: 샘플링 결과로 정렬 점수 계산

5단계: 정렬 점수에 따라 브랜드/배너 순서 결정 후 노출
```

## 5. 도입 후 달라진 점

무신사는 MAB 정렬 시스템 도입 이후 다음과 같은 변화를 경험했습니다.

**다양한 브랜드에 노출 기회 분산**
기존에는 상위 고정 브랜드로 트래픽이 집중됐지만, 실시간 성과와 사용자 관심도를 복합적으로 고려해 더 많은 브랜드가 상위 노출 기회를 가질 수 있게 됐습니다.

**실시간 순위 재정렬**
시간의 흐름과 성과에 따라 순위가 동적으로 조정됩니다. 한번 상위에 올랐다고 영원히 상위에 머무르지 않습니다.

**탐색 기회 보장**
성과가 낮은 브랜드도 일정 수준의 노출 기회(탐색)를 가지게 됩니다. 덕분에 숨겨진 가능성 있는 브랜드를 발굴할 수 있습니다.

**기간 조정으로 유연한 대응**
Druid에 저장된 로그 데이터의 기간을 조정하면서 노출 영역별 특성에 맞게 정렬을 조정할 수 있습니다. 예를 들어, 트렌드 변화가 빠른 영역은 짧은 기간의 데이터를, 안정적인 영역은 긴 기간의 데이터를 사용합니다.

결과적으로 **해당 영역의 클릭률(CTR)이 상승**했다고 합니다.

## 6. 내가 배운 것

### MAB는 A/B 테스트의 진화된 버전이다

A/B 테스트는 실험 기간 동안 두 버전에 트래픽을 고정 비율로 나눕니다. 성과가 나쁜 버전에도 계속 트래픽이 흘러들어 기회비용이 발생합니다.

MAB는 실시간 성과를 반영해 좋은 쪽에 트래픽을 점점 더 몰아주면서도, 나쁜 쪽도 완전히 포기하지 않고 탐색 기회를 유지합니다.

```
A/B 테스트: 결론을 낸 뒤 → 배포
MAB:        탐색하면서 동시에 → 배포 (실시간 최적화)
```

### Thompson Sampling이 실무에서 각광받는 이유

확률적 샘플링이라는 점이 처음엔 직관적이지 않았지만, 이 방식 덕분에 불확실성이 높은 아이템(데이터가 적은 아이템)이 자연스럽게 더 자주 탐색되는 것을 이해했습니다. 명시적으로 ε 같은 하이퍼파라미터를 튜닝하지 않아도 탐색과 활용의 균형이 자동으로 맞춰진다는 것이 강점입니다.

### 데이터 파이프라인 설계가 알고리즘만큼 중요하다

아무리 좋은 알고리즘도 실시간 데이터가 제때 들어오지 않으면 소용이 없습니다. Kafka로 실시간 수집하고 Druid로 집계해서 저장하는 파이프라인이 없었다면 MAB를 실시간으로 운영하는 것 자체가 불가능했을 것입니다.

### Rollup은 시계열 데이터 최적화의 핵심이다

로우 로그를 그대로 쌓으면 저장소가 금방 가득 찹니다. Druid의 롤업처럼 "시간 단위로 집계해서 저장"하는 전략은 MAB가 필요로 하는 "기간별 클릭/노출 수"를 효율적으로 관리하는 핵심 아이디어였습니다.

## 7. 더 공부하고 싶은 것

- **Thompson Sampling의 수학적 배경**: Beta 분포와 베이지안 추론의 관계를 더 깊이 이해하고 싶습니다.
- **컨텍스트 밴딧(Contextual Bandit)**: 사용자 개인화 정보까지 고려하는 LinUCB 같은 알고리즘으로 확장하면 어떻게 달라지는지 궁금합니다.
- **Apache Druid vs ClickHouse**: 유사한 목적의 시스템을 어떤 기준으로 선택하는지 비교해보고 싶습니다.
- **Regret 최소화**: MAB 알고리즘을 평가하는 지표인 "누적 후회(Cumulative Regret)"를 직접 계산해보고 싶습니다.
