# 소프트웨어 기획 설계 — 요구사항 정의부터 API 명세까지

---

## 0. 전체 흐름과 각 단계의 역할

소프트웨어 설계는 다음 순서로 진행된다. 각 단계는 이전 단계의 결과물을 입력으로 받는다.

```
요구사항 정의서
  "무엇을 만들 것인가"
        │
        ▼
화면설계서
  "사용자는 어떻게 사용하는가"
        │
        ▼
DB 스키마
  "데이터를 어떻게 저장할 것인가"
        │
        ▼
API 명세서
  "프론트엔드와 백엔드는 어떻게 통신할 것인가"
```

순서가 중요한 이유는 앞 단계의 결정이 뒤 단계를 제약하기 때문이다. 화면에서 필요한 데이터를 DB에 저장하지 않으면 API가 줄 수 없고, 요구사항에 없는 기능을 화면에 넣으면 범위가 흔들린다. 반대 방향으로 설계하거나 단계를 건너뛰면 나중에 큰 수정 비용이 발생한다.

---

## 1. 요구사항 정의서

### 핵심 목적

요구사항 정의서는 **"이 시스템이 무엇을 해야 하는가"를 팀 전체가 동의하는 형태로 기록**하는 문서다. 개발을 시작하기 전에 기획자·개발자·QA가 같은 기준을 가지게 한다.

요구사항이 명확하지 않으면 개발이 진행될수록 "그게 원래 있어야 했나요?" 같은 질문이 반복되고, 뒤늦게 기능을 추가하면서 설계가 뒤틀린다.

### 기능 요구사항 vs 비기능 요구사항

많은 사람들이 기능 요구사항만 생각하고 비기능 요구사항을 빠뜨린다. 둘의 차이는 다음과 같다.

**기능 요구사항**: 시스템이 **무엇을 해야 하는가**
```
사용자는 이메일과 비밀번호로 로그인할 수 있다.
기업을 검색하면 기업명과 종목코드를 확인할 수 있다.
```

**비기능 요구사항**: 시스템이 **어떻게 동작해야 하는가**
```
일반 화면은 3초 이내에 응답해야 한다. (성능)
비밀번호는 단방향 해시로 저장해야 한다. (보안)
Chrome, Edge, Safari 최신 버전을 지원해야 한다. (호환성)
```

비기능 요구사항은 개발 막바지에 "아, 이것도 해야 하나?"로 발견되면 구조를 바꿔야 하는 경우가 생긴다. **보안·성능·호환성은 처음부터 명시해야 한다.**

### MoSCoW 우선순위

모든 기능을 같은 비중으로 다루면 일정이 무너진다. 각 기능에 우선순위를 부여해야 한다.

```
Must   — 없으면 서비스 자체가 불가능한 기능
Should — 있어야 하지만, 없어도 서비스는 동작하는 기능
Could  — 있으면 좋지만 우선순위가 낮은 기능
Won't  — 이번 버전에서는 하지 않는 기능
```

**흔한 실수**: 모든 기능을 Must로 정의하는 것. Must가 너무 많으면 사실상 우선순위가 없는 것과 같다. MVP(최소 기능 제품) 범위를 먼저 확정하고, 나머지를 Should·Could로 분류하는 것이 현실적인 개발 계획의 출발점이다.

### 요구사항을 잘 쓰는 기준

좋은 요구사항은 **측정 가능하고 검증 가능**해야 한다.

```
❌ 나쁜 예: 빠르게 응답해야 한다.
✅ 좋은 예: 정상 네트워크에서 요청 후 3초 이내에 주요 콘텐츠를 표시해야 한다.

❌ 나쁜 예: 안전하게 저장해야 한다.
✅ 좋은 예: 비밀번호는 bcrypt 또는 Argon2id 방식으로 해시하여 저장해야 한다.
```

"빠르게", "안전하게", "쉽게" 같은 표현은 나중에 완료 기준을 만들 수 없다. 요구사항은 QA가 테스트 케이스로 변환할 수 있는 형태여야 한다.

### ID 체계와 추적성

요구사항이 많아지면 "이 화면은 어떤 요구사항을 구현하는가?", "이 요구사항은 어디에서 확인하는가?"를 추적하기 어려워진다. 처음부터 ID 체계를 정의하면 이 연결을 유지할 수 있다.

```
기능 요구사항:   REQ-FUNC-001
비기능 요구사항: REQ-NFN-001
화면:           SCR-AUTH-001
```

추적성 매트릭스(Traceability Matrix)는 요구사항과 화면·API가 양방향으로 연결되어 있는지 확인하는 표다. "이 화면을 빼면 어떤 요구사항이 구현되지 않는가?"를 즉시 파악할 수 있어야 한다.

## 2. 화면설계서

### 핵심 목적

화면설계서는 **사용자가 어떤 경험을 하게 되는가**를 정의한다. 기능 요구사항을 사용자의 행동 흐름으로 변환하는 단계다. 프론트엔드 개발자는 이 문서를 기준으로 UI를 구현하고, 백엔드 개발자는 어떤 API가 필요한지 파악한다.

### 화면 목록을 먼저 정의한다

설계를 시작하기 전에 **어떤 화면이 있고 어떻게 연결되는지** 전체 지도를 그린다. 화면 하나씩 설계하기 전에 전체 구조를 먼저 파악해야 누락되는 화면이 없다.

각 화면에는 ID, 이름, 서비스 내 위치(Depth), 주요 목적을 정의한다. Depth를 명확히 하면 화면 간 이동 방향이 자연스럽게 정해진다.

### 화면 디스크립션의 구성 요소

와이어프레임만으로는 "이 버튼을 누르면 어떻게 되는가"를 설명하기 부족하다. 각 화면은 다음 항목으로 설명되어야 한다.

**화면 구성**: 화면에 존재하는 UI 요소를 번호와 함께 나열한다. 번호는 사용자 동작·오류 문구 설명에서 참조할 때 사용한다.

**사용자 동작**: 사용자가 어떤 행동을 하면 어떤 일이 일어나는지 순서대로 서술한다. 이 흐름이 나중에 API 호출 순서가 된다.

```
검색창에 기업명 입력
  → 검색 API 호출
  → 검색 결과에서 기업 선택
  → 리서치 시작 버튼 클릭
  → AI Research 생성 API 호출
  → 성공 시 researchId를 기준으로 다음 화면으로 이동
```

**검증**: 입력값에 어떤 규칙이 적용되는지 명시한다. 클라이언트 검증과 서버 검증을 구분하는 것이 중요하다.

> 클라이언트 검증은 UX를 위한 것이고, 서버 검증은 보안을 위한 것이다. 클라이언트 검증을 통과해도 서버에서 반드시 재검증해야 한다. 브라우저 개발자 도구로 클라이언트 검증은 언제든 우회할 수 있기 때문이다.

**오류 문구**: 발생 가능한 모든 오류 상황과 사용자에게 보여줄 메시지를 미리 정의한다.

```
이메일 미입력    → "이메일을 입력해주세요."
이메일 형식 오류 → "올바른 이메일 형식을 입력해주세요."
인증 실패        → "이메일 또는 비밀번호가 올바르지 않습니다."
```

오류 메시지를 미리 정의하지 않으면 개발자마다 다른 문구를 쓰게 된다. 특히 **보안 관점에서 오류 메시지가 불필요한 정보를 노출하면 안 된다.** 예를 들어 "존재하지 않는 계정입니다"는 공격자에게 계정 존재 여부를 알려준다. 인증 실패 메시지는 이메일과 비밀번호 불일치를 구분하지 않고 통일하는 것이 좋다.

**인수 조건 (Acceptance Criteria)**: 이 화면이 완성됐다고 판단하는 기준을 구체적으로 명시한다. QA 테스트 케이스의 기준이 된다.

```
AC-001: 이메일을 입력하지 않은 상태에서는 로그인 버튼을 누를 수 없다.
AC-002: 올바른 이메일과 비밀번호로 로그인하면 메인 화면으로 이동한다.
AC-003: API 요청 중에는 로그인 버튼이 비활성화되어 중복 클릭이 방지된다.
```

### 예외 처리 정책 표

화면의 예외 상황을 표로 정리하면 개발·QA 모두 명확한 기준이 생긴다.

| 상태 | 발생 조건 | 처리 방식 | HTTP 코드 |
|---|---|---|---|
| 정상 | 인증 성공 | 메인 화면으로 이동 | 200 |
| 잘못된 입력 | 이메일 형식 오류 | 필드 하단 오류 문구 | 400 |
| 인증 실패 | 비밀번호 불일치 | 인증 실패 메시지 | 401 |
| 로딩 중 | API 응답 대기 | 버튼 비활성화 + Spinner | - |
| 서버 오류 | 내부 오류 | "잠시 후 다시 시도해주세요." | 500 |

### Happy Path만 설계하면 안 된다

화면설계서에서 가장 흔한 실수는 정상 흐름만 그리는 것이다. 실제 사용자는 네트워크가 끊기거나, 잘못된 값을 입력하거나, 다른 사용자의 데이터에 접근하려고 시도한다. **빈 상태(Empty State), 로딩 상태, 오류 상태를 정상 흐름과 함께 설계해야 한다.**

## 3. DB 스키마 설계

### 핵심 목적

DB 스키마는 **서비스에서 다루는 데이터를 어떻게 저장하고 관계 지을 것인가**를 결정한다. 화면설계서에서 표시해야 하는 데이터, API가 주고받을 데이터를 역추적해서 필요한 테이블과 컬럼을 정의한다.

### 도메인을 먼저 파악한다

테이블을 하나씩 설계하기 전에 서비스의 핵심 도메인 객체가 무엇인지 먼저 파악한다. 도메인이 명확해야 테이블 간의 경계가 자연스럽게 정해진다.

예를 들어 AI 금융 리서치 서비스라면 사용자·기업·Research·수집 데이터·리포트·추가 질문이 핵심 도메인이다. 각 도메인이 어떤 관계를 맺는지 그림으로 정리한 다음 테이블 설계로 넘어가는 것이 좋다.

### 설계할 때 반드시 챙겨야 할 것들

**공통 컬럼 표준화**

모든 테이블에 동일한 감사(Audit) 컬럼을 추가한다. 나중에 빠뜨린 테이블에 컬럼을 추가하면 ALTER TABLE 비용이 발생한다.

```sql
created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
updated_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP
```

**Soft Delete 설계**

중요한 데이터는 물리적으로 삭제하지 않고 상태값으로 관리한다. 사용자 탈퇴 시 계정을 즉시 삭제하면 해당 사용자가 작성한 데이터의 참조 무결성이 깨질 수 있고, 감사 추적도 불가능해진다.

```sql
status     VARCHAR(20) NOT NULL DEFAULT 'ACTIVE'  -- ACTIVE / WITHDRAWN
deleted_at TIMESTAMP NULL                          -- 삭제 시점 기록
```

**상태값 설계**

복잡한 프로세스는 상태값으로 전체 흐름을 표현한다. 상태 전이 다이어그램을 그려보면 어떤 상태가 필요한지, 어떤 전이가 허용되는지 명확해진다.

```
PENDING → RUNNING → COMPLETED
                 ↘ FAILED
```

허용되지 않는 상태 전이(예: COMPLETED → RUNNING)를 애플리케이션 레벨에서 차단해야 한다.

### 관계 설계의 핵심 원칙

**M:N 관계는 반드시 중간 테이블로 해소한다**

사용자가 여러 기업을 관심기업으로 등록하고, 한 기업은 여러 사용자의 관심기업이 될 수 있다면 M:N 관계다. 이는 반드시 중간 테이블로 표현해야 한다.

```
users ↔ companies  →  watchlists(user_id, company_id)
```

중간 테이블에 복합 유니크 제약을 걸면 중복 등록을 DB 레벨에서 방지할 수 있다.

**1:1 관계에서 어느 테이블에 FK를 두는가**

Research와 Report가 1:1 관계라면 Report 테이블이 Research ID를 FK로 가지는 것이 자연스럽다. Research는 Report가 없어도 존재할 수 있지만(진행 중), Report는 반드시 Research에 속하기 때문이다.

**현재 데이터와 시점 데이터를 분리한다**

예를 들어 기업의 현재 주가 데이터와 특정 분석 시점의 주가 데이터는 별도 테이블로 관리해야 한다. 현재 데이터만 있으면 과거 분석 결과를 나중에 조회할 때 수치가 달라진다. 금융 서비스에서 **분석 기준시점 고정은 신뢰성의 핵심**이다.

### 인덱스 전략

인덱스는 조회 성능을 높이지만 삽입·수정 성능을 낮춘다. 무조건 많이 걸면 오히려 성능이 나빠질 수 있다.

```
인덱스가 필요한 컬럼
  - WHERE 조건에 자주 등장하는 컬럼 (ex. user_id, status)
  - JOIN에 사용되는 FK 컬럼
  - 정렬(ORDER BY)에 자주 사용하는 컬럼

인덱스가 필요 없는 컬럼
  - 카디널리티가 낮은 컬럼 (ex. BOOLEAN, 2~3개짜리 ENUM)
  - 거의 조회하지 않는 컬럼
```

UNIQUE 제약을 걸면 자동으로 인덱스가 생성된다. 중복 방지를 위해 UNIQUE 제약을 건 컬럼에 별도 인덱스를 추가할 필요는 없다.

## 4. API 명세서

### 핵심 목적

API 명세서는 **프론트엔드와 백엔드가 어떻게 통신할 것인가에 대한 계약서**다. 이 계약이 명확하면 프론트엔드와 백엔드가 병렬로 개발할 수 있다. 명세 없이 구두로 약속하면 개발 중에 계속 "이거 어떻게 받아요?"라는 질문이 생긴다.

### REST API 설계 원칙

REST API는 리소스(Resource) 중심으로 URL을 설계하고, HTTP 메서드로 행위를 표현한다.

**URL은 리소스(명사)로 표현한다**

```
❌ /getCompanyList       → 동사 기반 (REST 원칙 위반)
✅ /api/companies        → 리소스 기반

❌ /createResearch
✅ /api/research         → POST 메서드가 "생성" 의미를 담음

❌ /api/user/1/getResearch
✅ /api/users/me/research → me를 쓰면 userId를 URL에 노출하지 않아도 됨
```

**계층 관계는 URL 구조로 표현한다**

```
/api/research/{id}/report          → 특정 Research의 리포트
/api/research/{id}/report/pdf      → 리포트의 PDF 버전
/api/research/{id}/questions       → 특정 Research의 추가 질문

/api/users/me/favorites            → 내 관심기업 목록
/api/users/me/favorites/{companyId} → 특정 관심기업
```

단, 계층이 너무 깊어지면 URL이 복잡해진다. 일반적으로 3단계 이상은 재검토를 권장한다.

### HTTP 메서드와 멱등성

| 메서드 | 의미 | 멱등성 |
|---|---|---|
| GET | 조회 | ✅ 여러 번 호출해도 결과 동일 |
| POST | 생성 | ❌ 호출할 때마다 새 리소스 생성 |
| PUT | 전체 수정 | ✅ 같은 요청 여러 번 = 같은 결과 |
| PATCH | 부분 수정 | ❌ (구현에 따라 다름) |
| DELETE | 삭제 | ✅ 이미 삭제된 것을 다시 삭제해도 결과 동일 |

**멱등성**은 같은 요청을 여러 번 보내도 결과가 동일한 성질이다. 네트워크 오류로 요청이 재전송될 때 중요하다. POST는 멱등하지 않으므로, 네트워크 재시도 시 중복 생성이 일어날 수 있다. 이를 방지하기 위해 클라이언트가 Idempotency Key를 헤더에 포함하는 방식을 쓰기도 한다.

### HTTP 상태 코드 선택 기준

상태 코드는 클라이언트가 응답을 파악하고 적절하게 처리하기 위한 신호다. 모든 응답을 200으로 처리하고 본문에 success: false를 담는 방식은 REST 원칙에 맞지 않는다.

```
2xx 성공
  200 OK          → 조회·수정 성공
  201 Created     → 새 리소스 생성 (POST 성공)
  204 No Content  → 성공이지만 반환 데이터 없음 (DELETE 성공)

4xx 클라이언트 오류 (요청 자체가 잘못됨)
  400 Bad Request → 잘못된 입력값, 형식 오류
  401 Unauthorized → 인증 없음 또는 만료 → "당신이 누구인지 모름"
  403 Forbidden    → 인증됐지만 권한 없음 → "당신은 알지만 이건 안 됨"
  404 Not Found    → 요청한 리소스가 없음
  409 Conflict     → 중복 충돌 (관심기업 중복 등록, 중복 요청)
  429 Too Many Requests → Rate Limit 초과

5xx 서버 오류 (서버가 처리에 실패)
  500 Internal Server Error → 서버 내부 오류
  504 Gateway Timeout → 외부 서비스 응답 초과
```

**401 vs 403을 헷갈리면 안 된다.** 401은 로그인이 필요하다는 의미이고, 403은 로그인은 됐지만 해당 리소스에 접근할 권한이 없다는 의미다. 다른 사용자의 데이터에 접근하려 할 때는 403이 맞다.

### 응답 구조 통일

API마다 응답 형식이 다르면 프론트엔드에서 처리 로직이 제각각이 된다. 성공·실패·목록 응답의 구조를 프로젝트 전체에서 통일해야 한다.

```json
// 단건 성공 응답
{ "data": { ... } }

// 목록 성공 응답 (페이지네이션 포함)
{
  "data": [...],
  "page": 0,
  "size": 10,
  "totalElements": 42,
  "totalPages": 5
}

// 실패 응답
{
  "error": {
    "code": "COMPANY_NOT_FOUND",
    "message": "해당 기업 정보를 찾을 수 없습니다.",
    "status": 404
  }
}
```

에러 코드(`COMPANY_NOT_FOUND`)를 별도로 정의하면 클라이언트가 메시지 문자열을 파싱하지 않고 코드 기반으로 분기 처리할 수 있다.

### OpenAPI(Swagger) 명세 작성

API 명세는 자연어로 설명하는 것보다 **OpenAPI 표준 형식으로 작성**하는 것이 좋다. YAML로 작성하면 Swagger UI가 자동으로 시각화해주고, 프론트엔드 개발자가 직접 API를 테스트해볼 수 있다.

```yaml
/api/auth/login:
  post:
    tags: [Auth]
    summary: 로그인
    requestBody:
      required: true
      content:
        application/json:
          schema:
            type: object
            required: [email, password]
            properties:
              email:
                type: string
                format: email
              password:
                type: string
                minLength: 8
    responses:
      "200":
        description: 로그인 성공
        content:
          application/json:
            schema:
              properties:
                accessToken:
                  type: string
      "401":
        description: 이메일 또는 비밀번호 불일치
```

인증이 필요한 API는 `security` 필드로 명시한다. 이렇게 하면 Swagger UI에서 토큰을 입력해 인증이 필요한 API를 테스트할 수 있다.

```yaml
security:
  - bearerAuth: []
```

### API 설계에서 보안을 챙겨야 하는 부분

**`/me` 패턴 사용**

`/api/users/{userId}/research`처럼 userId를 URL에 노출하면 다른 사람의 userId를 넣어 데이터를 조회하려는 시도가 생긴다. `/api/users/me/research`처럼 me를 쓰면 서버가 토큰에서 userId를 추출하므로 더 안전하다.

**클라이언트에서 받은 값을 그대로 신뢰하지 않는다**

예를 들어 Research 생성 요청에 기업 ID가 포함되어 있더라도, 서버에서 해당 기업이 실제로 존재하는지 다시 검증해야 한다. 클라이언트는 얼마든지 임의의 값을 전송할 수 있다.

**민감 정보는 응답에 포함하지 않는다**

비밀번호 해시, API Key, 토큰 등은 응답 본문이나 에러 메시지에 포함되면 안 된다. 에러 로그에 포함되는 것도 주의해야 한다.

## 5. 단계 간 연결이 핵심이다

각 단계를 잘 작성하는 것도 중요하지만, **단계 간 연결이 일관성 있게 유지되는 것이 더 중요하다.**

화면에서 보여주는 데이터가 DB에 저장되어 있지 않으면 API가 줄 수 없다. 요구사항에 없는 기능이 화면에 들어가면 범위가 흔들린다. API 응답에 있는 필드가 화면에서 사용되지 않으면 불필요한 데이터를 전송하는 것이다.

추적성(Traceability)을 유지한다는 것은 **요구사항 ID가 화면에 연결되고, 화면이 API에 연결되고, API가 DB 테이블에 연결되는 흐름이 끊기지 않아야 한다**는 의미다. 이 연결이 끊기는 지점이 구현 누락이나 설계 불일치가 발생하는 곳이다.

| 개념 | 한줄 요약 |
|---|---|
| **기능 요구사항** | 시스템이 무엇을 해야 하는가 — 측정·검증 가능하게 |
| **비기능 요구사항** | 시스템이 어떻게 동작해야 하는가 — 보안·성능·호환성 |

| **인수 조건** | 완성 기준 — QA 테스트 케이스의 원본 |
| **클라이언트 검증 vs 서버 검증** | 클라이언트는 UX, 서버는 보안 — 둘 다 필요 |
| **Soft Delete** | 물리 삭제 대신 상태값으로 관리 — 감사 추적·참조 무결성 |
| **상태 전이** | 허용된 상태 변화만 가능하도록 애플리케이션에서 제어 |
| **M:N 중간 테이블** | 다대다 관계는 반드시 중간 테이블로 해소 |
| **멱등성** | 같은 요청 여러 번 = 같은 결과 — GET·PUT·DELETE는 멱등 |
| **401 vs 403** | 401은 인증 없음, 403은 권한 없음 |
| **응답 구조 통일** | 성공·실패·목록 응답 형식을 프로젝트 전체에서 통일 |
| **추적성** | 요구사항 → 화면 → API → DB가 끊기지 않고 연결되어야 함 |
